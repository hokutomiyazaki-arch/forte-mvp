# Twilio SMS 設定手順（CEO作業）

> CC からは登録できない。アカウント作成に**本人確認・クレジットカード**が要り、
> 日本向けの送信者名（Alphanumeric Sender ID）を使う場合はさらに**事業者としての審査**が入るため、
> ほくと本人の名義で行う必要がある。
> コード側は先に入れてあり、**下の3つの環境変数が入った瞬間に動き出す**（未設定の間は何も起きない）。

## 入れてほしい環境変数（Vercel）

| 変数名 | 値 | どこで取るか |
|---|---|---|
| `TWILIO_ACCOUNT_SID` | `AC` で始まる文字列 | Console トップの Account Info |
| `TWILIO_AUTH_TOKEN` | Auth Token | 同上（表示ボタンを押すと出る） |
| `TWILIO_SMS_FROM` | 購入した番号（`+1...`）または登録済み送信者名 | 下の手順3 |

3つ揃って初めて有効になる。1つでも欠けたら**従来どおり**（プロが電話する流れ）に落ちる。

## 手順

### 1. アカウント作成
https://www.twilio.com/try-twilio から登録 → メール認証 → SMS認証。

### 2. 有料アカウントに切り替える（必須）
**無料トライアルのままでは実運用に使えない。**
- トライアルは「認証済みの番号」にしか送れない＝お客さまに届かない
- Alphanumeric Sender ID は**有料アカウント限定**

Console 右上の **Upgrade** からクレジットカードを登録する。初回は $20 程度チャージすれば足りる。

### 3. 送信元を用意する（どちらか）

**A. 米国番号を買う（すぐできる・推奨の第一歩）**
- Console ＞ Phone Numbers ＞ Buy a number ＞ United States ＞ **SMS 対応**にチェック
- 月額 $1.15 程度
- **Twilio は日本の電話番号を販売していない**ので、番号を使う場合は海外番号になる
- お客さまには国際番号（+1…）から届く。少し怪しく見えるのが弱点

**B. 送信者名（Alphanumeric Sender ID）を登録する（見栄えが良い・審査あり）**
- 送信元が `+1...` ではなく `REALPROOF` のような文字列で届く
- Console ＞ Phone Numbers ＞ Regulatory Compliance / Trust Hub から登録申請
- **事前登録が必要で、キャリア審査に数日かかる**。会社情報の提出を求められる
- 登録した文字列は**大文字小文字まで完全一致**で使うこと（カリアが厳密に照合する）
- 弱点: 送信者名からは**返信できない**（一方通行）

> 進め方の提案: **まず A で動かす**（当日から使える）。運用に乗ってから B を申請して差し替える。
> `TWILIO_SMS_FROM` を書き換えるだけで切り替わる。

### 4. Vercel に環境変数を入れて再デプロイ
Project ＞ Settings ＞ Environment Variables に上の3つを入れる。
**入れただけでは反映されない。再デプロイが要る。**

### 5. 動作確認

**① 設定が読めているかを、送らずに確かめる**
ブラウザで https://realproof.jp/api/pro/sms-test を開く。

```json
{"ok":true,"enabled":true,"account_sid_configured":true,
 "auth_token_configured":true,"from_configured":true,"from_looks_like_number":true}
```

`enabled: false` なら3つのどれかが入っていないか、**再デプロイがまだ**。
どれが欠けているかは各項目で分かる（値そのものは返さない）。
`from_looks_like_number: false` は送信者名（Alphanumeric Sender ID）を入れた場合は正常。
番号のつもりで入れたのに false なら `+81`/`+1` の付け忘れ。

**② 自分の携帯に1通テストする**
プロとしてログインした状態で、`/api/pro/sms-test` に POST する。
スマホなら、ダッシュボードを開いたタブで開発者ツールが使えないので、
**PCのブラウザでログイン → コンソールで下を実行**するのが早い。

```js
await fetch('/api/pro/sms-test', { method: 'POST' }).then(r => r.json())
```

- 送信先は**プロフィールに登録済みの自分の電話番号に固定**されている
  （宛先を指定できるようにすると、ログインさえすれば任意の番号へ我々の課金でSMSを
  送れる踏み台になるため。テストのために穴は開けない）
- `no_phone_on_profile` → プロフィールに電話番号が入っていない
- `phone_not_mobile` → 固定電話・桁数違い。SMSは携帯(070/080/090)にしか届かない
- `send_failed` → Twilio側で弾かれた。Console の Monitor ＞ Logs ＞ Messaging にエラーが出る

**③ 本番の流れを通す**
間違ったメールアドレスで予約を1件入れる → バウンス webhook が動く →
入力した携帯にSMSが届き、**プロ側には「電話してください」が出ない**ことを確認する。

## 料金の目安

- 日本の携帯宛て: **1通あたり $0.089 前後**（¥13前後）
- 米国番号の維持費: **月 $1.15 前後**
- 全予約には送らない（後述）ので、月に数百通いくような使い方にはならない

## いつ送るか（実装済み・および今後）

| タイミング | 状態 | 理由 |
|---|---|---|
| **バウンス検知の直後** | **実装済み** | メールが死んだ瞬間。ここが本命 |
| 支払いリンクを出して数時間、未払い・未開封 | 未実装 | バウンスしない不達（迷惑メール・キャリア遮断）はこれでしか拾えない。件数はバウンスより多いはず |
| 前日リマインド | 未実装 | ノーショー対策。件数が少なく効果が大きい |

**全予約には送らない。** コストもだが、通知チャネルは使い減りする。

## 越えてはいけない線（重要）

- **本文にPIIを書かない。** 名前も金額も日時も書かず、短いリンクだけ送る
  （SMSは家族と共有の端末で見られることがある）。実装もそうなっている。
- **取引の連絡と販促を混ぜない。**
  - 予約金の支払い案内・リマインド = **取引**。番号を預かった目的そのものなので送ってよい
  - リワードの案内・新機能のお知らせ = **販促**。同意なしに送るとクレームとブロックが一気に来る
    （メールと違って逃げ場がないので体感が強い）
  - 販促SMSを始めるときは、**明示的なオプトインのチェックボックスを先に作る**
