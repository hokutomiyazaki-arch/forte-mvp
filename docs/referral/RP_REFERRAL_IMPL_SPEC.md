## 0. 実装ルール（厳守）

1. **本番稼働中のアプリである。** すべての変更は Preview branch で検証 → 動作確認後に main へ merge
2. **機能追加は「コードを先にデプロイ → 環境変数で ON/OFF」の順序。** 問題が出たら環境変数削除で即時ロールバック
3. **用語ルール**：「実力」は使わない → 「**強み**」。医療用語を避ける（症例→**サポート実績**／主訴→**テーマ**／治療・改善→サポート・変化）。
   **「処方箋」は内部用語であり、UIに出さない**（医療用語であり、ヨガ・テニスコーチ・マジシャン等に通じない）。
   UI表示は「**紹介**」「**紹介リスト**」。クライアント向けの「あなたの先生からのご紹介」とも整合する。
   **上下関係を含む語をUIに出さない**：門下・弟子・師匠 → **認定者／指導者**。「育成プルーフ」は内部用語で、
   ユーザー向け表示は「**認定者が積み上げた実績**」。対象職種は整体・鍼灸・トレーナー・ヨガ・ピラティス・
   テニスコーチ・エステティシャン・マジシャン等に及ぶため、特定業種を前提とする語（ゴッドハンド・患者・
   施術者など）も避け、**クライアント／サポート**を基本語彙とする
4. **保証は絶対に自動生成しない。** 人の推薦・所属・代理関係は、必ず本人または権限者の明示的アクションを経由する
5. 既存データは削除・破棄しない。移行する
6. **UI品質ルール**：絵文字を装飾として使わない（💻📣✨等）。安っぽく見え、
   「検証された証明」というブランドと相反する。ステータスを示す3色ドットのように
   **機能として意味を持つ記号は可**。副次的な導線（例：オンライン向けの案内）は
   背景色やアイコンで目立たせず、静かなテキストリンク＋シェブロンに留める。
   主導線と副導線の視覚的な重さを逆転させない
7. **保存手段のない入力欄を作らない**。入力欄には必ず保存ボタンか、
   保存された旨の明示的フィードバックを伴う自動保存を付ける

### 機能フラグ一覧（環境変数）
```
FEATURE_REFERRAL_LISTS      # 処方箋リスト機能（値: "off" | プロID列挙 | "all"）
FEATURE_REFERRAL_BOOKING    # 紹介経由の予約・決済
FEATURE_AI_TEXT_SANITIZE    # Voice等の表示時AI変換
FEATURE_ORG_CARD            # 団体カード（育成プルーフ）
FEATURE_SEARCH_PRIVATE      # 検索ページの非公開化
FEATURE_PROOF_UNIQUE_COUNT  # ユニーク/累計の2本表示
```

### 段階公開（アローリスト方式）
`FEATURE_REFERRAL_LISTS` は3値で運用する:
- 未設定 / `off` → 全員に非表示
- `id1,id2,id3`（プロIDのカンマ区切り）→ **該当プロにのみ作成UIを表示**（先行アクセス）
- `all` → 全員に公開

実装ルール:
- 判定はサーバー側の共通ヘルパー1関数に集約（`isReferralEnabled(proId)`）。UI出し分けとAPIガードの両方で同じ関数を使う
- **クライアント向け処方箋ページ（共有URL）はゲートしない**。リストを作れるのが先行者だけなので、閲覧側の制限は不要
- 先行期間は最大2週間。1件成立 or 2週間経過の早い方で `all` に切替（Vercel環境変数の変更＋再デプロイのみ、コード変更なし）
- 60日ゲートの起算日は **`all` 切替日**とする

## 1. 事前調査タスク（実装前に必ず実行し、結果を報告）

### 1-1. クライアント⇔プロの紐付け調査
既存の「プルーフ投票 → LINE登録」フローで、クライアントがどのプロに紐付いているかを確認する。

確認項目:
- 投票（プルーフ）テーブルのスキーマ：voter識別子（voter_id / normalized_email 等）と対象プロID
- クライアント側テーブルに `line_user_id` 相当のカラムがあるか
- 「クライアント → 最初に投票したプロ」を引くクエリが成立するか

**目的**: 成立するなら、既存の全プルーフから招待網（アトリビューション台帳）を遡って再構築できる。
これがリファラルフィー計算の土台になる。

### 1-2. プルーフ分布の調査
- プロ別プルーフ数の **中位値（median）** と分布（平均は上位が引き上げるため不可）
- ユニーク投票者数 vs 累計投票数の比率（プロ別）
- 「常連」タグの付与ロジックと該当者数
- 定着110人のうち、プルーフ15件以上に到達している人数

### 1-3. 既存「お気に入り」機能の調査
- テーブル名・スキーマ・レコード件数
- 片方向か相互か、通知の有無、公開されているか

## 2. スキーマ変更

### 2-1. 処方箋リスト（referral_lists / referral_list_items）

```sql
-- リスト本体
create table referral_lists (
  id uuid primary key default gen_random_uuid(),
  owner_id uuid not null references professionals(id) on delete cascade,
  title text not null,                    -- 例: "名古屋圏・めまい/ふらつき"
  comment text,                           -- 選定基準の説明（送り手が語るのは「基準」）
  visibility text not null default 'link' -- 'link' | 'private' | 'public'
    check (visibility in ('link','private','public')),
  criteria jsonb,                         -- 動的条件（下記）
  slug text unique,                       -- 共有URL用
  is_delegate boolean default false,      -- 「私の代わりに」リストとして指定されているか
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);

-- リストの構成要素（ピン指名のみ格納。基準行は criteria から動的生成）
create table referral_list_items (
  id uuid primary key default gen_random_uuid(),
  list_id uuid not null references referral_lists(id) on delete cascade,
  pro_id uuid not null references professionals(id) on delete cascade,
  note text,                              -- 一人ずつへの一言
  sort_order int default 0,
  consent_status text not null default 'pending' -- 'pending'|'approved'|'declined'
    check (consent_status in ('pending','approved','declined')),
  created_at timestamptz default now(),
  unique (list_id, pro_id)
);
```

`criteria` の想定構造:
```json
{
  "org_id": "uuid|null",
  "themes": ["vestibular", "postpartum"],
  "min_support_records": 10,
  "requires_reassessment": true,
  "area": { "prefecture": "愛知県", "radius_km": 30 },
  "accepting_only": true
}
```

**ルール**:
- ピン指名は **1リストあたり最大3名**（人への保証の上限）
- 基準行は人数無制限。表示時にリアルタイム絞り込み
- 表示順は「ピン（特に推薦）」→「基準を満たす方」の2ブロック
- クライアントへの提示は **合計2〜4名まで**（5名以上は選択不能になるため上限を設ける）

### 2-2. 受け入れステータス

```sql
alter table professionals add column accepting_status text default 'closed'
  check (accepting_status in ('open','conditional','closed'));
alter table professionals add column accepting_note text;      -- 条件付きの内容
alter table professionals add column accepting_updated_at timestamptz;
alter table professionals add column delegate_list_id uuid references referral_lists(id);
```

**UI配置（先行テスト第3弾で再変更）**:
- 受付ステータスは**「ダッシュボード」見出しの直上に、背景なしの3段スライダー**として置く。
  指で左右にスライドして切り替える：**🔴停止中 ⇔ 🟡代理リストで案内 ⇔ 🟢紹介受付中**
  - ホームタブ内の情報密度が既に高いため、そこに足さない。見出し上の余白を使う
  - `accepting_status IS NULL` は **open として扱い、ノブは🟢の位置**に置く（⚪️中立位置は廃止）
  - **🟡を選ぼうとした時、有効な代理リスト（承諾済み＋受付中のメンバー1名以上）が無い場合は
    選択させず、代理リスト設定画面へ誘導する**（空約束の防止。§2-2の🟡点灯条件は維持）
- **公開カードページ**：受付中のときのみ「🟢 新規のご紹介を受付中」を表示。
  停止中は**何も表示しない**（受付ステータスは「紹介の受付可否」であって「営業しているか」では
  ないため、赤表示はクライアントの誤解と離脱を招く）
- **ステータスは2値、表示は3色**（先行テストのフィードバックにより確定）:
  - **データ**：`accepting_status` は `open` / `closed` の**2値**。`conditional` は廃止
    （openと挙動が完全に同一で、条件の中身は自由記述のため機械判別もできず、状態を増やす価値がない。
    また「トグルで即切替」は2値でないと成立しない）。既存の conditional レコードは open に寄せる
  - **⚪️未設定は廃止。全員の初期状態を🟢受付中とする**（先行テスト第3弾で確定）。
    状態は**3色のみ**：
    - 🟢 **受付中**（`open`。**NULL も open として扱う**＝fail-open）
    - 🟡 **停止中・代理リストで案内**（`closed` ＋ 有効な代理リストあり）
    - 🔴 **停止中**（`closed` ＋ 代理なし）
  - 理由：⚪️を残すと「全体公開の初日にほぼ全員が未設定」という鶏と卵が発生し、
    リストが1つも作れない。既定ONにして「嫌な人は外してください」と**宣言する**方が、
    ユーザーの手間も実装の複雑さも小さい
  - 実装：**コード側でNULLをopenとして扱う**（これによりデータ移行を待たずに⚪️がUIから消える）。
    あわせて `ALTER TABLE professionals ALTER COLUMN accepting_status SET DEFAULT 'open'`。
    既存NULLの一括UPDATEとNOT NULL化は、**全体公開の告知と同じタイミング**で行う
    （告知前に既存プロの公開カードが勝手に「受付中」になるのを避けるため、
    公開カードのバッジ表示はフラグで抑えたまま `all` 切替まで出さない）
  - 告知文に必ず含める：「**紹介の受付は初期状態でONになっています。
    受け付けたくない場合はホーム画面のスライダーでオフにしてください**」
  - 全員が既定🟢になるため、フィルタ「紹介につながる人のみ表示」は🔴を除くだけの機能になる
  - **掲載と受付を分離する**（先行テスト第3弾で方針変更）。詳細は §3-1 参照。
    掲載は承諾ゲートなし（即時掲載＋事後辞退）、受付ステータスは本人が自分のトグルで決める。
    **承諾を根拠に accepting_status を自動で open にする実装は撤回**
    （他人の行動を根拠に本人の公開状態を変えるのは越権）
  - **クライアント向け /r/ ページには「実際に受けられない候補」を選択可能な状態で出さない**。
    🔴（停止中・代理なし）の候補は「現在受付停止中」と明示し、予約ボタンを出さない。
    選べるのに409で弾かれるのは最悪のクライアント体験になる
  - **🟡の点灯条件は「代理リストが設定されている」だけでは不十分**。
    そのリストに **承諾済み（consent_status='approved'）かつ受付中（🟢）のメンバーが1名以上**
    存在する場合のみ🟡とする。空のリストや全員停止中のリストで
    「ご案内できます」と表示するのは**空約束**であり、保証を自動生成しない原則に反する。
    条件を満たさない場合は🔴として扱う
  - 🟡は3段スライダーで**直接選択できる**。ただしデータ上は `closed` ＋ 代理リスト設定の
    **複合操作**として保存する（accepting_status は open/closed の2値のまま変えない）。
    有効な代理リストが無い状態で🟡を選んだ場合は確定させず、代理リスト設定画面へ誘導する。
    トグル自体は🟢⇄🔴の2値のまま。本人のダッシュボードでも
    「停止中（代理リストで案内中）」とラベルを添えて混乱を防ぐ
  - **条件メモ（accepting_note）は「表示モード⇔編集モード」で作る**。
    常時テキストエリアを開いたままにしない：既定は本文がラベルとして表示され（未入力なら
    「条件を追記する」のリンク）、タップで編集モードに入り、**保存ボタン**で確定して表示モードへ戻る。
    保存後は「保存しました」を短く出す。保存手段がない入力欄は作らない
  - 条件メモは受付中のときのみ表示し、
    紹介リストの候補カードと公開カードに小さく表示（例：「めまい・ふらつきのケースのみ」「土曜のみ対応可」）
- **プロ向け一覧・検索**：「**紹介につながる人のみ表示**」のフィルタ切替を設ける（デフォルトはOFF＝全件）。
  対象は 🟢 ＋ 🟡。送り手が知りたいのは「このピンが誰かの施術につながるか」であって
  本人が受けるかではないため、🟡（代理あり）を含める。プロ向け画面では🔴も明示してよい
- **公開カードページの3分岐**：
  - 🟢 → 「新規のご紹介を受付中」＋条件メモ
  - 🟡 → 「**現在は新規のご紹介を受け付けていませんが、信頼できる先生をご案内できます**」
  - 🔴 → 何も表示しない

**表示ロジック（重要）**:
- **基準行（自動生成）**: `accepting_status = 'closed'` のプロは**静かに除外**する
- **ピン指名**: 除外しない。「現在受付停止中」と表示し、`delegate_list_id` があれば**一段だけ**展開表示する。なければ停止中表示のみ
- 代理リストの入れ子は**一段のみ**。再帰しない
- 代理リストは**本人が明示的に設定した場合のみ**。自動生成は禁止

### 2-3. サービスメニューと標準価格（価格つり上げ対策）【STOP 1決定：pro_menus拡張】

新テーブルは作らない。既存 `pro_menus`（38行・price_textテキスト型）を拡張する：

```sql
alter table pro_menus add column price_jpy int;              -- 紹介成立価格（正確な数値）
alter table pro_menus add column duration_min int;
alter table pro_menus add column is_referral_bookable boolean default false;
alter table pro_menus add column external_price_url text;    -- 価格照合バッチ用
```

**ルール**:
- 紹介経由の予約は `is_referral_bookable = true` かつ `price_jpy` 設定済みのメニューでのみ成立
- 既存の price_text 表示は変更しない（NULL列追加のみで既存表示は無影響）
- 表示価格と紹介成立価格を同一レコードで管理し、内部の価格乖離を構造的に防ぐ
- 予約ごとの値付け欄は作らない

## 2-4. 紹介予約と決済

```sql
create table referral_bookings (
  id uuid primary key default gen_random_uuid(),
  list_id uuid references referral_lists(id),
  sender_pro_id uuid references professionals(id),      -- 送り手（処方箋を書いた人）
  receiver_pro_id uuid not null references professionals(id),
  client_id uuid not null references clients(id),
  menu_id uuid references pro_menus(id),
  theme_tags text[],
  preferred_slots jsonb,          -- 第1〜第3希望
  confirmed_at timestamptz,
  status text not null default 'requested'
    check (status in ('requested','confirmed','completed','cancelled','expired')),
  price_jpy int not null,
  fee_total_bps int not null default 4000,   -- 40.00%
  fee_sender_bps int not null default 2800,  -- 28.00%
  fee_platform_bps int not null default 1200,-- 12.00%
  stripe_payment_intent_id text,
  info_share_consent boolean default false,
  expires_at timestamptz,          -- requested から48時間
  completed_at timestamptz,
  created_at timestamptz default now()
);
```

**フロー**:
1. クライアントが処方箋ページから先生を選択
2. 第1〜第3希望を送信（カレンダー連携なし）
3. テーマ確認＋本人の補足入力
4. **情報共有の同意**チェック（送り手からの引き継ぎ情報を受け手に共有）
5. **Stripe でオーソリ（与信確保）のみ**。請求は施術完了時にキャプチャ
6. 受け手が希望から1つ選んで確定。**48時間無反応で自動 expired** → 送り手とクライアントへ通知＋別候補提案
7. 施術完了ボタン → キャプチャ → フィー自動分配 → プルーフ依頼をLINE送信
8. **紹介経由で生成されるプルーフには client_id を必ず紐付ける**（votes.client_user_id 全null の轍を踏まない）

**フィー（段階導入）**:
- **Phase 1：合計33.6%（送り手30%／決済実費3.6%／リアプルの利益0%）。**
  Stripe手数料は実費としてそのまま差し引き、リアプルは1円も受け取らない。
  「リアプルの取り分は0円、決済会社への実費のみ」と説明できる状態にする
  （※実費を項目として最初から置くことで、Phase 2は「新規追加」ではなく
  「既存項目の率変更」になり、心理的抵抗が大幅に下がる）
- **Phase 2：合計40%（送り手28%／システム利用料12%＝決済実費を含む）。**
  月間紹介件数が安定し、成功譚が複数立った後に、**事前告知の上で**導入する
- 料率は `fee_*_bps` カラムで予約ごとに保持し、既存予約に遡って適用しない（値上げの遡及禁止）
- **初回のみ**。2回目以降は課金しない
- **ワンホップ厳守**: 金は直接の紹介・指導関係の一段のみを流れる。中継のみでは0円

金額例（初回10,000円 / Phase 1）:
```
クライアント支払      10,000
 ├ 決済実費(Stripe)      -360
 ├ 送り手フィー        -3,000
 └ 受け手の入金         6,640
リアプルの収益              0
```

**入金（Stripe Connect Express を Phase 1 から採用）**:
- **現金**（RPクレジットではない）。プロ間の紹介料は事業所得のため
- **Stripe Connect Express** を使用。受け手・送り手の双方にConnectアカウントを作らせる。
  KYC（本人確認）はStripeのホスト型画面が担当するため実装は軽く、
  RPは口座情報・本人確認書類を保持しない（プロへの説明時の安心材料になる）
- 構成は **Separate Charges and Transfers**（プラットフォームで一括決済 → 受け手・送り手へ個別transfer）
- `on_behalf_of` で受け手を売主に設定し、施術売上がRPの売上に計上されない形にする（経理をシンプルに）
- **料率は `application_fee_amount` を予約作成時に算出して設定する。**
  Phase 1（0円）→ Phase 2（12%）の移行は**設定値の変更のみ**で完了し、
  プロ側の再手続き・再登録は一切不要。この点が手動振込より優れている最大の理由
- 入金スケジュールはConnect側で設定（週次または月次）

**オンボーディングの体験設計（摩擦の最小化）**:
- **Connectアカウントは1つで送り手・受け手を兼用**（役割ごとに別登録は不要）
- **受け手としての要求タイミング**：「**受付中トグルをONにする瞬間**」
  （紹介リクエストが来てから要求すると、その案件を逃す）
- **送り手としての要求タイミング**：**処方箋の作成・共有は絶対にブロックしない**（未登録でも可）。
  フィーが発生した時点で「**¥3,000のお受け取りが保留されています**」と具体的な金額を提示し、
  そこから口座登録へ誘導する。金額が見えている瞬間が最も登録意欲が高い
  - 満枠のプロは受付トグルをONにしないため受け手経路では登録されない。送り手側の導線が必須
  - 保留期間は90日。未登録のまま経過した場合の扱い（繰越／失効）を規約に明記
  - **受け取り辞退の選択肢を用意する**（善意で紹介した人に金銭を押し付けない。
    辞退できることが「金のためではない」という自認を守り、紹介の動機が汚染されるのを防ぐ）
  - ダッシュボードに「保留中の受け取り ◯円」を常時表示（最も強い登録動機）
- 直前に1画面で理由を説明：「紹介料をお受け取りいただくための口座確認です。
  口座情報と本人確認書類はStripe（決済会社）が管理し、リアプルは保持しません」
- 所要5〜10分（氏名・生年月日・住所・業種・口座・本人確認書類の撮影）。所要時間を事前に明示する
- Stripeのホスト画面はロゴ・ブランドカラーを設定して違和感を減らす
- **初回入金は審査で数日かかる**ことを事前告知（「入金されない」という不安の最大の原因）
- **高齢層のサポート導線**：書類撮影で詰まる人が出るため、LINEで運営が伴走できる窓口を用意
- サイクル：施術完了 → **保留期間14日**（キャンセル・トラブル対応）→ 入金
- 源泉徴収・支払調書・消費税/インボイス・預り金の扱いは税理士に確認
- ※**クライアント間の紹介**（価値4）は現金ではなく**RPクレジット**（譲渡・現金化不可、期限付き）。
  プロ間＝現金／クライアント間＝クレジット、と明確に分ける

**開示ルール**:
- **クライアントへ**：手数料の**存在と「あなたの料金は変わりません」を明示**。内訳（28/12等）は表示しない
- **受け手のプロへ**：**合計料率を必ず明示**（本人が支払う費用のため）

**⚠️ 当初案の誤り（Claude Code の調査で判明・修正済み）**:
- `role` カラムは**既に存在**する（`011_org_members.sql`: `role TEXT NOT NULL DEFAULT 'member'
  CHECK (role IN ('member','manager'))`）。ADD COLUMN は 42701 で失敗し、
  CHECKを回避しても `founder`/`instructor` への UPDATE が 23514 で弾かれる

- 所属確定の判定は既存の `status` カラムと二重化する（既存コードは `status='active'` と
  `accepted_at` を併用）

**修正方針：既存 `role` には触らない。** 既存の role は**権限**の軸（member/manager）であり、
今回必要なのは**育成カードを表示するか**という別の軸。同じカラムに2つの意味を載せると、
CHECK制約の付け替えと既存データのUPDATEという不可逆な操作が必要になる。

```sql
alter table org_members add column growth_role text

alter table org_members add column aggregate_opt_in boolean default true;
alter table org_members add column growth_visibility text default 'public'
  check (growth_visibility in ('public','private'));
```
- 既存 `role`（member/manager）は権限用として**そのまま維持**。データ移行不要
- 育成カードを表示するのは `growth_role in ('founder','instructor')` の本人ページのみ
- `certified_at` は新設せず **`accepted_at` を起算点**として使う

#### 集計VIEW（新設）【列名・条件を修正済み】
```sql
create or replace view org_growth_summary as
with members as (
  select om.organization_id, om.professional_id, min(om.accepted_at) as joined_at
  from org_members om
  where om.status = 'active'                      -- ★既存カラム。二重化を避けず両方見る
    and om.accepted_at is not null
    and om.removed_at is null
    and coalesce(om.aggregate_opt_in, true) = true
    and coalesce(om.growth_visibility,'public') = 'public'
    and om.growth_role is null                    -- ★代表・講師自身は育成側の分子から除外
  group by om.organization_id, om.professional_id
)
select m.organization_id,
  count(distinct m.professional_id)                          as member_count,
  count(v.id)                                                as growth_proof_count,
  count(v.id) filter (where v.created_at > now() - interval '30 days') as last_30d,
  count(distinct v.normalized_email)                         as unique_clients
from members m
left join votes v
  on v.professional_id = m.professional_id
  and v.created_at >= m.joined_at        -- ★所属確定後の実績のみ計上
  and v.vote_type in ('proof','continuation')
group by m.organization_id;
```
※ `org_members` は professional 1人につきバッジごとに複数行あるため、
members CTE で `group by` して重複を潰してから join すること。
別VIEWで「認定者の強みTOP5分布」も作る（selected_proof_ids を unnest し、
**DISTINCT normalized_email** で人数集計。§2-8のDISTINCT原則に揃える）。

### 2-8. 2回目以降の投票＝継続記録（スタンプ）【Phase 0.5・Phase 1に先行実施】

**目的**: 反復投票の社会的気まずさ（同じ人に同じ賞賛を再度求める）を、設問の変更で解消する。

**入力**:
- 投票画面の最初に本人選択：「この先生の施術を受けるのは → 初めて／2回目以降」
- **初めて** → 現行フロー（強み項目の選択あり）
- **2回目以降** → スタンプUI：「今回も受けました ✓」ボタン1つ（必須はこれのみ）＋任意の一言（前回からの変化）＋任意のテーマ。強み項目の選択は表示しない
- 送信時に normalized_email × professional_id で過去票を照合（既存の週次制限照合を流用）
  - 「初めて」選択なのに過去票あり → エラーにせず受理。集計上は継続記録扱い（選択項目は行に保存、集計不算入）
  - 「2回目以降」選択なのに過去票なし → 受理して新チェーン開始。self_reported_repeat フラグ。ヒント表示「前回と同じメールアドレスだと記録がつながります」
- クライアント側に「あなたの記録：◯回目」を表示（ポイントカード体験）

**データ**: `vote_type = 'continuation'` を追加。selected_proof_ids は空。

**集計**:
- 累計プルーフ：初回✅／継続✅（どちらも+1）
- ユニーク人数：初回のみ
- 常連（3票以上×初回から90日以上）：継続で積む
- 強み項目：初回のみ。継続は不算入

**強み項目の集計規準を「票数」→「人数（DISTINCT normalized_email）」に全面変更**:
- vote_summary VIEW をDISTINCT集計に改修。表示は「◯人が選んだ」
- 過去データ：行は一切削除・変更しない（グランドファザリング）。ただし表示は全プロ一律で人数規準になるため、反復票を持つプロの強み項目の見かけの数字は下がる。**全体の単位変更として一度だけ告知**（「票→人に表示を変更しました。積み上げた記録は全て保存されています」）
- 累計プルーフ数（メインの数字）は変わらない

**⚠️ 物理成果物（カード・賞状）は必ずスナップショットから生成する**（集計変更で実害が出たため追加）:
- カード・賞状の記載内容を**ライブのVIEWから生成してはいけない**。
  申請時点の集計値を `card_applications.stats_snapshot`（jsonb）等に凍結保存し、
  カードと賞状は**同一のスナップショットから生成**する
- これをやらないと、①申請後に集計方法が変わると発行できなくなる
  ②カードと賞状が別タイミングで生成され記載が食い違う、という事故が起きる
- **申請済み分は申請時点の基準で発行する**（遡及して条件を厳しくしない。
  グランドファザリング原則の物理成果物への適用）
- 集計方法の変更は**告知を先に、変更を後に**。物理成果物が絡む変更では順序を逆にしない
- 実テーブル名：申請＝`certification_applications`（`proof_count_at_apply` を元から保持）、
  賞状＝`certificates`。カード・賞状・発送は共通ヘルパー `getCertStatsForPro` に一元化し、
  必ず同一の値から生成する
- **値の決定ルール**：「申請時スナップショットを下限、ライブ値とのproof単位max」。
  申請時に条件を満たしていた人は集計方式が変わっても発行される（グランドファザリング）、
  実績が本当に伸びれば昇格も反映され、既発送分が後から転落しない
- **下限（フロア）が効くのは、その申請に対してのみ**。同一プロによる将来の新規申請は
  ライブ値のみで判定する（旧方式の数字を恒久的に持ち越すと、後から入った人より
  ティア到達が容易になる不公平が固定化するため）
- スナップショット取得に失敗した場合は**ライブ値にフォールバックせずエラーで停止**する
  （誤った数字で物理カードを刷らないため。fail-closed）

**意図的な不正の扱い（設計判断として記録）**:
- 反復客に毎回「初めて」を押させる行為 → DISTINCT集計により同一メールでは盛れない。放置で可
- 家族・知人による別メールでの反復「新規」投票 → 対面ゲート（NFC/QR・週1制限）が物理コストを課しており、盛れる上限は数ユニーク程度でスケールしない。検知システムは作らない（過剰防衛）。将来、決済連動プルーフ（金の裏書き付き）が導入されれば自然に重みの差がつく

### 2-9. 外部プロの招待（処方箋リスト経由）【Phase 1に含める】

**目的**: 処方箋リスト作成時に、RP未登録のプロを招待できるようにする。
「同業からの敬意の通知」として届く、最も断りにくい獲得経路。

**フロー**:
1. リスト作成画面で「RP外のプロを追加」→ 名前＋連絡手段（LINE共有 or URLコピー）を入力
2. 招待URL発行。招待状の文言：
   「**◯◯先生が、あなたを"信頼できる連携先"としてリストに登録しようとしています。**
   プロフィールを作成すると、紹介を受けられるようになります」
3. 被招待者が登録完了 → **リストに即時掲載**（`consent_status='approved'`。§3-0の承諾ゲート撤廃に統一）。
   登録直後に「◯◯さんの紹介リストに掲載されました。紹介されたくない場合は
   ホーム画面の受付スライダーをオフにしてください」を表示・通知する
4. 招待者には登録完了を通知

**データ**: `referral_invites`（id / list_id / inviter_pro_id / invitee_name /
invite_token unique / registered_pro_id nullable / created_at / registered_at）

**共有方法（第3弾で追加）**:
- 招待URLは**コピーだけでなくネイティブの共有UIを開く**（Web Share API `navigator.share`）。
  LINE・メール等にそのまま渡せるようにする。非対応環境（一部のデスクトップ）では
  コピーにフォールバックし、両方のボタンを併置する
- 共有テキストは事前に入っている状態にする（送り手が編集できる）。例：
  「REALPROOFという、施術の実績が記録として残るサービスを使っています。
  信頼できる連携先として登録したいので、よければプロフィールを作ってもらえませんか。→ {URL}」
- **招待トークンは1人分（single-use）**。`registered_pro_id` が入った時点で消費とし、
  以後そのURLでアクセスした人には「この招待は既に使用されています」と表示して登録させない
  （1つのURLが拡散して多数が登録する事態を防ぐ）
- 発行画面に明示する：「**この招待URLは1人分です（◯◯先生用）。
  別の先生には新しいURLを発行してください**」
- 招待時の名前入力は必須のまま（1対1の招待であることを担保）

**ルール**:
- 招待に金銭報酬は付けない（プロ招待の報酬はネットワーク価値と将来の被リスト数。
  金銭を付けると招待が営業に変わり、敬意の通知でなくなる）
- 招待経由の登録は `referral_invites.registered_pro_id` で計測（獲得経路の分析用）
- 招待の乱発防止：未登録招待の同時保留は1人あたり10件まで

### 2-10. プロ間連絡＝案件スレッド（汎用DMは作らない）【Phase 1に含める】

**方針**: 汎用のダイレクトメッセージ機能は実装しない。

`booking_participants`（booking_id / pro_id / role / share_bps）へ外出しし、既存2カラムから
バックフィルする。**分配処理は最初から「参加者リストを回して配る」形の関数として実装**しておくこと
（参加者2人でも4人でも同じコードで動く形にすれば、移行コストが大幅に下がる）。

## 3. 既存機能の改修

### 3-0. 掲載の承諾ゲートを撤廃する【先行テスト第3弾で方針変更】

**変更前**：ピン追加 → 相手に承諾依頼 → 承諾されて初めてリストに載る（承諾ゲート）
**変更後**：**ピン追加した時点で即時掲載**。相手には通知が飛ぶ。辞退は**受付トグルをオフ**にすること

理由：承諾を必須にすると、相手がメールを見ない限り紹介が永久に成立しない。
クリティカルパス上に他人の行動を置く設計は流量を殺す。

**「掲載」と「受付」を分離する**:
- **掲載**（誰のリストに載るか）＝送り手が決める
- **受付**（紹介を受けるか）＝**本人だけが決める**（ホームのスライダー）＝これが唯一のオプトアウト手段
- リスト単位の辞退機能は作らない（MVPでは過剰。閉じたネットワークで送り手が信用を賭けて
  選んでいるため、全体トグルで十分。実際に苦情が出たら per-list 辞退を追加検討）
- **承諾を根拠に accepting_status を自動で open にする実装は撤回・削除**
  （他人の行動で本人の公開状態を変えるのは越権）

**掲載可否のルール（相手のステータス別）**:
| 相手 | ピン追加 | 通知文面 |
|---|---|---|
| 🟢 受付中 | 可 | 「◯◯さんがあなたを紹介リストに追加しました。紹介されたくない場合は受付トグルをオフにしてください」 |
| 🟡 代理あり | 可 | 同上 |
| 🔴 停止中 | **不可** | ピン追加時に「この先生は紹介の受付を停止中です」と表示してブロック |

- 全員の初期状態が🟢なので、掲載できない相手は「自分で明示的に停止した人」だけになる
- **consent_status の扱いは2種類に分ける**：
  共有リスト（link/public）のピン＝`approved` で即時掲載／
  private（連携候補）のアイテム＝**`pending` 固定**。
  private を approved にすると、後で visibility を link に変えた瞬間に無通知で一斉公開される穴が空く
- **allowlist期間中（`FEATURE_REFERRAL_LISTS` がID列挙の間）は、掲載対象もallowlist内のプロに限る**。
  対象外プロへのピン追加はブロックする。テスト中に無関係なプロへ通知が飛ぶのを防ぐため。
  `all` 切替で自動解除
- **掲載中の本人には、allowlist外でも受付スライダーと accepting API を開放する**。
  掲載・予約流入が始まるのに本人がオフにできないのは罠になるため
  （招待経由で登録したプロが該当）
- 🔴を掲載不可にすることで、**通知文面が常に意味を持つ**（既に停止中の人に「いやならオフに」は無意味）
- 実際の紹介（予約リクエスト）到着メールは**件名を明確に区別**する
  （掲載通知＝静かな通知／紹介到着＝目立つ件名）

### 3-0-2. プロを探す導線と連携候補【第3弾・撤回と再指示】

**⚠️ 前回の「連携候補セクションを廃止する」という指示は誤りだったので撤回する。**
連携候補（非公開）は「♡気になる」で保存した相手の一覧であり、表示として正しい。
問題は存在ではなく、**そこから紹介リストへ直接移せないこと**。移せないなら置いてある意味がない。

**大原則：リスト名を先に決めないとプロを選べない、という順序を廃止する。**
「まず器を作れ」は業務の実際と逆。プロは「この先生を紹介したい」から始まる。

**追加の入口は2つ。どちらからでもリストが生まれる**:
1. **連携候補の各行から直接**（前回削除してしまった導線を復活させる）
2. **プロを探すページから**（新規に探す場合）

いずれの場合も「紹介リストに追加」を押したら**追加先の選択が出る**：
既存リスト一覧 ＋「**新しいリストを作る**（その場で名前を入力）」。
つまり**最初のプロを追加する操作の中でリストが生まれる**。空のリストを先に作る手順は不要。

- ダッシュボードから「新しい紹介リストを作る」フォームは**主導線から降格**
  （残してもよいが、上部の主役はリスト一覧と追加導線）
- **UI文言に内部用語・パスを出さない**：`/search`、`♡ 気になる`、`除去` のような
  開発上の呼称を画面に出さない。ナビの既存ラベルと日常語に揃える
  （例：「プロを探す」「気になる先生」「外す」）
- **横スクロールを発生させない**：招待URL発行ブロックを含め、
  実機幅360〜390pxで要素がはみ出さないこと

### 3-1. 「お気に入り」機能をリスト機構に統合

現状のプロ同士のお気に入りを、処方箋リストの前段として再定義する。**2層に分ける**：

| 層 | 名称案 | 性質 | 通知 | 公開 |
|---|---|---|---|---|
| 第1層 | **連携候補**（旧お気に入り） | 個人的なブックマーク。責任を伴わない | なし | 非公開 |
| 第2層 | **紹介リスト掲載** | 保証を伴う。クライアントに提示される | あり（掲載通知のみ・承諾ゲートなし／§3-0） | リンク共有 |

**移行方法**:
- 既存のお気に入りレコードを、各ユーザーの `referral_lists` に「連携候補」という
  `visibility='private'` のデフォルトリストとして自動生成し、そこへ `referral_list_items` として移行する
- 移行時 `consent_status = 'approved'` としない（非公開リストなので同意不要だが、
  ただし**private（連携候補）内のアイテムは pending 固定とする**。
  approved にしてしまうと、後でそのリストの visibility を link に変更した瞬間に
  無通知で一斉公開される穴が空くため。**共有リスト（link/public）のピンは approved で即時掲載**、
  **private は pending 固定**、という二段構えにする）
- UI：連携候補から処方箋リストへ「追加」する導線を作る（リスト作成の摩擦を最小化）

**被リスト数の扱い**:
- 「何人のプロの**処方箋リスト**に載っているか」は将来の信頼指標になり得る（Googleの被リンクと同じ発想）
- ただし**第1層（連携候補）はカウントしない**。軽い行動を信頼指標に混ぜると値が薄まる
- Phase 1では集計のみ行い、**表示はしない**（数値の意味が安定してから公開）

### 3-2. 検索ページの非公開化

**方針**: クライアント向けの一覧検索は公開しない。クライアントは常に処方箋から入る。

**ただし「見つけてもらえなくなる」という誤解に注意**（LPには「技術を届けたい人が、あなたを見つける」と記載があり、
プロは検索露出を期待して登録している可能性がある）。

正確な仕様は以下：
- **一覧検索（クライアント向け）**: 非公開化する
- **個人プロフィールページ**: **本人の意思で公開可**（外を歩く名刺として機能させる）。
  プロは自分のInstagram・HPに貼れる。この経路は残す
- **プロ向け検索**: 残す。ただし用途を「連携できるプロを探す」に明示的に再定義する
- **検索の種類を2つに分ける**（現在1本に混在しているのが問題）:
  1. **施術検索**（誰がこのクライアントを診られるか）→ 臨床プルーフ × 地域 × 受け入れ状況
  2. **信用検索**（誰の判断・系譜を信頼できるか）→ 育成プルーフ・団体。**この軸が現在存在しない**

**プロ向けの説明文（UI内に明記）**:
「一覧検索は非公開になります。代わりに、あなたのプロフィールは
①同業のプロが連携先として探せる ②あなた自身が公開して名刺として使える ③紹介経由で指名される。
不特定多数に並べられて価格で比較されるのではなく、選ばれた形で届きます」

### 3-3. 「近隣で活躍するプロ」表示の方針転換

- **クライアント向けの近隣表示は廃止**（ポータル的な発見導線は方針に反する）
- **プロ向けに転換**：「**近くで連携できるプロ**」として残す。カードに
  「連携候補に追加」「処方箋リストに追加」ボタンを置き、**処方箋作成の入口**にする
- 表示時は `accepting_status` を必ず動的に反映

### 3-4. プルーフ表示をユニーク/累計の2本立てに

現状「1人毎週1回まで」であるため、累計数だけでは
「多くの人から支持されている」のか「少数が長期間支持している」のか区別できない。

**表示を3指標に変更**:
```
ユニーク ◯人 ／ 累計 ◯件 ／ 常連（同一プロへ3票以上かつ初回から90日以上）◯人
```
どちらも正当な勲章として扱う（継続の証明はリピート型のプロの武器になる）。
副作用として、少数の反復による数値の水増しが構造的に見分けられるようになる。

### 3-5. プルーフ発生率の改善（日常エンジン）

- **投票完了画面に導線を1行追加**：「あなたも証明を持てる」→ プロ登録へ
  （施術者は施術を受けるため、クライアントに同業が含まれる確率が高い。最安のプロ獲得経路）
- **週次リマインド**：「今週まだプルーフが0件です」（デイリーは不可）
- **常連タグを勲章化**：「3ヶ月連続で更新されている常連◯人」をプロフィールに表示し、
  プロ側が依頼する理由を作る
- **LP/説明文の修正**：現在「1人1回」と記載されているが実際は「1人毎週1回」。
  プロ側の認識のズレが発生数を抑制している可能性が高い。**最優先で修正**
- 依頼の摩擦低減：受付・タブレット常設・カード置きなど、**プロが口頭で頼まなくて済む形**を用意
- **店舗端末モード**：プロの端末でクライアント本人が入力できるようにする
  （高齢層のデバイス障壁対策。メールのみ・1人1回制限は維持されるため検証性は保たれる）

### 3-6. 価格照合バッチ（つり上げ対策）
`pro_services.external_price_url` を定期取得し、登録価格との乖離をAIで照合。
乖離が閾値を超えたら運営に通知（人力監視ゼロ）。規約に
「紹介経由と直接申込は同一メニュー同一価格」を明記。

感情曲線の設計：**不安（見放される？）→ 警戒（怪しい？）→ 安堵（先生が選んでくれた）→ 納得（透明）**

7. **共有される情報の範囲を明示**＋同意フロー

## 15. プロフィール表示の情報階層【2026-08-04・田中さんの提案から】

### 15-1. 原則
自己紹介は誰でも書ける。プルーフはRPにしかない。
よってRPにしかないものをページ上部に置く。誰でも書けるものを上に置くと、
RPは「無料のLPホスティング」になり、反・盛る文化という思想と矛盾する。

現状の問題：長文の自己紹介（1,500字級）を書いた人のページで、プルーフが3画面下に
押し下げられている。放置すると「1,500字書く人の次は2,000字書く人」という軍拡競争になる。

### 15-2. 表示順（確定）
名前・proofs数・バッジ → 強みプルーフTOP3 → 自己紹介（3行クランプ＋続きを読む）
→ 支持しているクライアント → タブ（強み全件／認定・資格／Voices／サービス・案内）
- 文字数制限はかけない（既存の文章を壊さない）。表示だけクランプする
- 「続きを読む」で全文が展開できること
- モバイル優先で確認（実機幅360〜390px）

### 15-3. 写真・動画の置き場
- Voiceへの写真添付は実装しない。理由3点：
  1. Voiceはクライアントの言葉であり原本をハッシュチェーンで保護している。
     プロが素材を足すと「検証済みの声」が「プロが編集した広告」に変わる
  2. 施術前後の写真は医療広告ガイドライン・景表法で最も厳しく見られる類型。
     レイヤー分離とAI変換で作った守りを自分から崩すことになる
  3. 身体の写真は肖像権・要配慮個人情報に該当し得る。モデレーション負荷も上がる
- 写真・動画（YouTube埋め込み含む）は「サービス・案内」タブに置く
  （ここは本人が自分を語る領域なので自由度を持たせてよい）
- 予約・連絡先ボタンをヘッダー近くにsticky固定する

### 16-8. 代理リストの再設計【2026-08-05】
**置き場所は「停止中プロの公開カード」。** 個人カードは名刺として単独流通するため
（Instagram・HP・NFCカード経由）、本人が停止中のとき訪問者は完全な行き止まりになる。

プロをご案内できます」＋**絞り込み2問（地域／どんなことでお困りですか）**
→ 該当者を最大4名。質問は最大2つ（3つ以上はアンケートになり離脱する）。

認定者が露出のために記録を貯める方向に動機が向く。
min_support_records は DISTINCT人数で判定。
掲載される認定者の同意は受付🟢が同意の表明（§3-0の掲載/受付分離と一貫）。

設定はスライダーと分離：スライダーは🟢⇄🔴の2値のまま。代理は別項目のチェックボックス

criteria の汎用作成UIは作らない（代理用の入力から criteria を生成する）。

### 16-9. 予約システムの直接予約への転用【2026-08-05】
紹介予約のために作った仕組み（SlotPicker・受付時間・通知・カレンダー連携）は
送り手がいないだけで直接予約とほぼ同一。カードに直接来た訪問者に開放する。

**これが解く最大の問題は頻度。** 紹介は年に数回だが直接予約は日常。
「実績が貯まる→カードが名刺になる→そこから予約が入る」の連結ができる。
（※収益試算の比較で決めた判断ではない。両方まだ0円であり、
判断根拠は「毎日使う理由ができるか」の一点）

**手数料は取らない。** 紹介の30%は送り手への報酬でRPは配管だが、直接予約には送り手が
いないため%を取れば純粋なプラットフォーム地代になる（クライアントはプロ自身の努力で
来ている）。逆選択も復活する（自前集客のある人が使わなくなる）。

**受付ステータスは1つに統一。** 紹介予約の受付中と個人カードの直接予約の受付中を
常に一致させる。スイッチが2つあるとプロが混乱しクライアントに矛盾が見える。
表記は「受付中／停止中」、補足に「紹介・直接予約の両方」。
（懸念：「紹介は止めたいが自分の客の予約は受けたい」という要望が出る可能性。
現段階は単純さ優先で1スイッチ。要望が出たら副オプション追加）

### 16-10. 直接予約に予約金は設けない【2026-08-05・確定】
**予約金は送り手に報酬を渡すために存在する。送り手がいなければ予約金も要らない。**
- 紹介予約：予約金あり（送り手報酬の原資・Stripe）
- 直接予約：**予約金なし・決済なし・リクエスト制のみ**（既存の無決済フローを流用）
利点：実装がほぼゼロ／返金・キャンセル・Connect・決済実費の説明が全て不要／説明が1行で済む。
すっぽかし防止機能は将来の有料機能の候補として温存する（今は実装しない）。

収益源の整理：NFCカード・賞状（全員）／紹介フィー Phase2の12%（成立した受け手）／
講座販売手数料／団体の法人契約／サブスク¥2,980（**FNT外から新規獲得したプロ**）。
FNT認定者は永久無料の約束を守る。FNT認定者はFNTの講座に対価を払っており、
金は別の扉から入っている（「天井のある事業が天井のない事業の獲得エンジンになる」と一貫）。
**課金の従量制限（月◯件まで無料等）は導入しない**（月末に予約受付を止める最悪の
インセンティブを生む）。
【要判断・未決】「FNT無料」の対象は現在の161名か将来の認定者も含むか。方針を明文化する。

### 16-11. トップページの価格表記を削除【2026-08-05・確定】
「通常月額2,980円が今は無料」等の表記を削除し「無料でご利用いただけます」のみにする。
理由：①景表法の二重価格表示リスク（実際に¥2,980で販売した実績がないため「通常価格」
として提示するのは有利誤認に該当し得る）②FNT認定者は永久無料と約束済みで
「今は無料」は事実と矛盾する ③「いつ課金されるのか」の不安を生み、無料→有料の転換は
SaaSで最も失敗する移行のため示唆するだけで離脱要因になる。
将来コールド獲得を始める際は、その層向けの別LPで実価格をそのまま提示する
（架空の通常価格でアンカリングしない）。新規ユーザーに後から価格を設定することは
可能なので、課金オプションは失われない。

### 16-12. 代理経由は無料・報酬なし／中抜きの整理【2026-08-05・確定】

**報酬が発生する線引き：人が名指しで保証したときだけ報酬が発生する。
criteria による自動抽出は保証ではない。**

| 経路 | 予約金 | 送り手報酬 |
|---|---|---|
| 紹介リスト経由（送り手が意図して作り特定のクライアントに手渡した） | あり33.6% | 30% |
| **代理経由**（本人が受けられないときの匿名トラフィックへの自動案内） | **なし** | **0円** |

代理経由は決済を発生させないリクエスト制で通す（§16-10の直接予約と同じ扱い）。
理由1：§16-10の原則から導かれる（名指しで保証する送り手がいない）。
理由2：同じサイト内に無料・前払い不要の直接予約があるため、代理経由で予約金を取ると
クライアントはその人を検索して直接予約するだけで回避できる。料金差ではなく
摩擦差（前払い・カード入力の有無）でバイパスが起きる。無料にすれば動機自体が消える。

**代理をONにする動機は金ではなく「囲い」**＝自分のクライアントが見知らぬ他人ではなく
自分が認定したプロに流れること。これは他の認定団体をRPに誘致する売り文句になる
（「あなたの団体で受けきれない需要が、あなたが認定した人に流れます」）。
UIの説明文もこの趣旨で書く（報酬を示唆しない）。

**紹介リスト経由のバイパスは防がず計測する。**
- 「紹介を受けているプロには直接予約を出さない」案は**却下**。そのプロが受ける予約は
  紹介経由の1件だけではないため、直接予約を止めると本人の通常の予約まで殺してしまう。
  プロの利益を損なう対策は採らない
- 対面で紹介された相手は紹介経由で予約する可能性が高い（関係性が働く）。
  ネットで偶然見つけた無関係な人はバイパスし得るが、それは元々紹介ではない
- 温存する手段：アトリビューション期間（/r/ 閲覧を記録し一定期間内の同一候補への
  予約を紹介として扱う）。**先に計測してから判断する**

**バイパスの実質的な抑止は「送り手が伝えること」。これを機能で支える（一斉送信はしない）**
⚠️ リスト共有時に候補全員へ一斉通知する形は採らない。3名のリストを渡してもクライアントが
選ぶのは1名で、残り2名には空振りの期待だけが残る。2回続けば通知が読まれなくなる。
現実の「ちゃんと伝えておきます」も、最も来そうな1人に個別に伝える行為である。
代わりに既存の仕組みへ最小限を足す2点：
1. **掲載通知に任意の一言を添えられる**（新しい画面を作らず既存通知に1フィールド追加）
   例：「めまいのケースでお願いすることがあるかもしれません」
2. **各候補行に「近日ご連絡があるかもしれません」を1タップで送れる**
   （送り手が選んだ1人だけに手動送信。リストの共有ボタンとは連動させない）
- どちらもクライアントのPIIは含めない（連絡先開示は決済後の原則を維持）
- スレッドは作らない（§2-10の汎用DMを作らない方針を維持。一方向の一言に留める）
- 同一相手・同一リストで24時間に1回までの連投制限を入れる
- 効果：①受け手が待ち構える状態になり紹介経由の予約が自然な流れになる
  ②送り手に「ちゃんと伝えておきます」と言える行動が生まれ、送り手側にも責任が発生する
  （「送り手はケースのオーナー」という位置づけの実装）

### 16-13. 既存の「予約する／相談する」ボタンの置き換え【2026-08-05】

【方針】置き換えるが、プロが選べる形にする。外部の予約システムを既に持っている
プロから取り上げないため、一律の置き換えはしない。
- 「RPで予約を受ける」ON → 予約するボタンがRPの予約リクエストフローへ
- OFF（既定・現状維持） → 従来通り外部の booking_url へ遷移

【「相談する」は mailto をやめてRP内フォームに置き換える】
理由：mailtoは記録が残らず、ダッシュボードで管理できず、迷惑メールにも弱い。
RP内フォームなら受け手のダッシュボードに残り、後から紹介予約に接続できる。
役割分担：「予約する」＝日時を選ぶ／「相談する」＝日時なしで問い合わせる
（高単価・審査制のサービスでは相談が先に来るのが自然なので両方残す）。

【外部HPの行き先】RP予約をONにした場合、外部の booking_url は LINKS内の1項目として残す。
公式HPは元々LINKSにあるためプロの資産は消えない。

【メニュー内に予約ボタンを置く】
予約可能なメニューのカード内に「この内容で予約する」を置き、
メニューを事前選択した状態で予約フォームへ進む。
- 出す条件は既存判定をそのまま使う：is_referral_bookable AND is_active AND price_jpy > 0
- 価格未設定・案内のみのメニューにはボタンを出さない。
  例：宮崎の「6ヶ月プレミアムパーソナル（まずは個別面談をお申し込み下さい）」は
  価格がなく実際の入口は別メニューなので、予約ボタンが出ると誤誘導になる。
  代わりに「相談する」への導線を置く
- フラグ名 is_referral_bookable は紹介専用に見えるが直接予約にも使う。
  UI上の表記は「オンライン予約を受け付ける」に統一する（カラム名は変更しない）

### 16-14. 代理案内の絞り込みは「質問ゼロ」に変更【2026-08-06・CEO決定・§16-8を上書き】
§16-8の「絞り込み2問（地域／どんなことでお困りですか）」は撤回する。
代わりに**訪問者に何も聞かず、停止中プロ本人の強みを基準に自動抽出する**。

理由：入力・選択は選択肢が何個であっても操作であり、停止中カードに来た訪問者は
「この人に頼みたかったのに受けてもらえない」という落胆の直後なので離脱しやすい。
そして訪問者が求めているのは「この人みたいな人」であり、それは本人の強みで表現できる。
（ワード入力案は却下：キーボードを出す操作は選択より重く、結果も既存の検索と同じになる）

**抽出ルール**
1. 停止中プロ本人の**実際に評価された強みTOP3**を取る（自己申告の selected_proofs ではなく
   投票実績＝vote_summary 系の集計を使う。本人が語る強みではなく市場が認めた強みを基準にする）
2. 同じ団体の**受付中**の認定者から、その項目のいずれかで実績がある人を集める
3. 該当が少ない場合は**同じカテゴリ（9分類）**まで広げる
4. **最終プルーフ日が新しい順に最大4名**（一致数順にしない。上位固定を避ける§16-8の原則を維持）
5. min_support_records（DISTINCT人数）の下限は従来どおり適用

**地域は任意のプルダウン**として候補リストの上に置く（初期状態は絞り込みなし）。
質問ゼロを守りつつ、遠方の訪問者だけが自分で絞れる。IP推定はしない（§16-8のまま）。

**設定UIの簡素化**：強みは自動算出になるためプロ側の入力は不要。
残る設定は「代理案内をON」「団体の選択」「実績下限」の3つのみ（founder/instructor限定は維持）。

### 16-15. 代理案内に「他の悩み用の検索ボックス」を併置【2026-08-06・CEO決定】
§16-14の自動抽出（本人の強みと類似の認定者を最大4名）だけでは、訪問者の悩みが
停止中プロの強みTOP3から外れている場合に応えられない。そこで**候補リストの下**に
検索ボックスを置く。

- **配置は候補リストの「下」**。上に置くと検索ボックスが最初に目に入り「入力しなければ」と
  感じさせるため、§16-14の質問ゼロの利点が消える。候補を見せた後の逃げ道として置く
- **検索範囲はその団体の認定者に限定する**。全プロ検索にすると「◯◯が認定したプロ」という
  保証が消えてただの検索窓になる（§16-12「代理をONにする動機は囲い」と一貫。
  他団体をRPに誘致する売り文句の根拠もここ）
- 受付中（🟢）の認定者のみを対象とする。並び順は§16-14と同じく最終プルーフ日の新しい順
- ラベルは「他のお悩みで探す」程度に小さく置く（主役は自動抽出された候補）

**却下：送り手プロに事前に検索させて人選を固定する案。**
理由は§16-8の「静的な人選はしない」原則に反するため。人選を固定すると選ばれた数名だけが
露出し続け、新しく認定された人が永久に出てこなくなる（動的抽出にした理由そのもの）。
運用の手間の問題ではなく設計原則の問題として却下する。

**補足**：この代理案内には送り手が存在しない（本人のカードに直接来た訪問者が対象）。
「送り手が何と言って紹介したか」が分からないのではなく、そもそも送り手がいない経路であり、
訪問者の来訪理由が不明という問題を検索ボックスで埋める、という位置づけ。

### 16-16. 代理案内は公開カード単体の経路に限定する【2026-08-06・CEO決定】
**紹介リスト（/r/[slug]）内での代理候補の展開表示を廃止する。**
§16-7で「紹介リスト内の入れ子としての代理リストは冗長」として撤回した方針を、
実装レベルでも完了させる（B-1では「§16-8まで維持」として一段展開を残していた）。

理由：紹介リストは**送り手が名指しで保証した**経路であり、そこに自動抽出の代理候補が
混ざると、クライアントから見て「送り手が選んだ人」と「criteriaが選んだ人」が同列に並ぶ。
§16-12で引いた「人が名指しで保証したときだけ報酬が発生する」という線引きが
視覚的に崩れ、直接の紹介であることの価値が薄まる。

- 撤去対象：`buildDelegateCandidates()`（referral-data.ts）と `/r/[slug]` 側の
  「現在受付停止中のため、代わりにご紹介できる先生です」子カード表示
- 代理案内が出るのは**停止中プロの公開カード（/card/[id]）のみ**（§16-8/16-14/16-15）
- 予約時のサーバー側検証（verifyReceiverAllowedInList）からも代理経路を外す
  （リストに載っていない受け手が紹介経由で予約できてしまう穴を残さない）

### 16-17. 表示する認定者の実績下限はオーナーが設定する【2026-08-06・CEO決定】
団体オーナー（＝代理案内を設定する founder/instructor）が「◯人以上から支持されている
認定者のみ表示」の下限を設定できるようにする（delegate_criteria.min_support_records）。

**単位は実人数（DISTINCT normalized_email）であり票数ではない。**
票数だと同一クライアントの複数回投票で水増しできるため（§2-8のDISTINCT原則と一貫）。
UIのラベルも「◯人以上から支持されている認定者のみ表示」とし、
「◯プルーフ以上」という票数を連想させる表記は使わない。

### 16-18. 直接予約の可否は自動判定／紹介予約だけを止める副オプション【2026-08-06・CEO決定】

**「RPで予約を受ける」の専用スイッチは作らない（自動判定）。**
予約可能なメニュー（is_active AND is_referral_bookable AND price_jpy > 0）が1件以上あれば
RPで予約を受ける意思表明とみなす。スイッチを増やすと§16-9の「スイッチが2つあると
プロが混乱する」と逆行するため。

**ただし「紹介予約だけ停止したい」は実在の要望なので副オプションを設ける。**
§16-9の「要望が出たら副オプション追加」を今回適用する。
- メインの受付トグル（🟢⇄🔴）＝**紹介・直接の両方**を止める（満枠時に1タップで全部止まる）
- その下に副オプション「紹介からの予約は受け付けない」チェックボックス
  → ONのとき紹介予約のみ停止し、直接予約は受け続ける
- 代理案内（§16-8/16-14）は「紹介を受けられない状態」で出す。したがって
  メイン🔴のときだけでなく、この副オプションONのときも出す
  （訪問者＝新規客を認定者へ流すのが目的なので、直接予約を受けていても矛盾しない）

### 16-19. 「相談する」はRP内フォーム＋往復メール【2026-08-06・CEO決定】

mailtoを廃止し、専用テーブルで受ける（referral_bookings は日時必須＋決済/送金の状態機械を
持つため流用しない）。

**動き方**
- クライアント：カードの「相談する」→ RP内フォームに**自分のメールアドレス**と相談内容を入力
- プロ：ダッシュボードの一覧で受け取り、**返信を書き込むだけ**でクライアントへメールが送られる
  （クライアントはメールでやりとり、プロはダッシュボードでやりとり）
- 日時の入力は不要（「予約する」＝日時を選ぶ／「相談する」＝日時なしで問い合わせる・§16-13）

**この形にする理由（CEO）**
1. 送信メールの下部に、後から**クライアントがプロを紹介する機能**の案内を入れられる
2. **クライアントリストが取れる**（メールアドレスが蓄積される）

**実装上の注意**
- クライアントのメールアドレスはPII。API レスポンスに含めない・プロのダッシュボードでのみ表示
- 既存の clients テーブル／ゲストクライアント作成（createGuestClient）の仕組みと整合させる
- スレッドは作るが、あくまで**そのクライアントとの相談1件に紐づく往復**であり、
  §2-10の「プロ↔プロの汎用DMは作らない」方針とは別物

### 16-20. 代理案内のソースは「団体」または「自作リスト」から選べる【2026-08-06・CEO決定】

団体を持っているプロはごく少数のため、団体からの自動抽出だけでは大多数のプロが
代理案内を使えない。**自分で作った紹介リストを代理案内のソースにできるようにする。**

| ソース | 人選 | 上限 | 使える人 |
|---|---|---|---|
| **団体**（criteria自動抽出） | その時点の条件で毎回動的に決まる（§16-14） | **4名** | founder/instructor |
| **自作リスト** | 本人が名指しで選んだ固定の顔ぶれ | **3名**（リスト自体の上限） | 全プロ |

- 代理案内の設定で「団体から自動で選ぶ」／「自分のリストから」を選択する
- 紹介リスト側に「代理案内に使う」チェックボックスを出す（**選べるのは1リストのみ**）
- 団体オーナーは両方から選べる（団体を持たない人は自作リストのみ）
- 保存は `professionals.delegate_criteria` を拡張: `{ enabled, mode: 'org'|'list', org_id?, list_id?, min_support_records? }`
  （既存の `delegate_list_id` カラムがあるが、設定を1箇所に集約するため delegate_criteria 側に統一する）
- 自作リストの場合も**受付中（🟢）のメンバーのみ**表示する（停止中の人を出すとまた行き止まりになる）

**【要判断・未決】自作リスト経由の予約に報酬を発生させるか。**
§16-12は「代理経由は無料・報酬なし」（criteriaの自動抽出は名指しの保証ではないため）と
決めたが、自作リストは本人が名指しで選んだ3名なのでこの理由が当てはまらない。
CC推奨は**報酬なしで統一**：①§16-12のもう一つの理由（無料の直接予約が同一サイト内にあるため
予約金を取れば検索して直接予約するだけで回避され、摩擦差でバイパスが起きる）は自作リストでも
同じ ②停止中にして代理リストを設定するだけで紹介料が入り続ける構造になり、
「送り手がクライアントに手渡しした」という紹介の実体から離れる。

### 16-21. 代理経由は報酬なしで統一／ただし経路は受け手に見せる【2026-08-06・CEO決定】
§16-20の【要判断】に決着。**自作リスト経由も報酬なし**（§16-12の代理経由と同じ扱い）。
criteria の自動抽出でも本人が名指しした自作リストでも、代理案内から来た予約に
紹介報酬は発生させない。

**ただし受け手プロの予約リストには経路を表示する。**
「◯◯さんからの紹介リスト経由」のように、誰の案内から来たのかを受け手に見せる。
報酬は出ないが、**誰の信頼を経由して来たクライアントか**は受け手にとって重要な情報であり、
送り手にとっても「自分の名前で人が動いた」という可視化になる。

実装上の含意：代理経由の予約でも**送り手（＝代理案内を設定した停止中プロ）は記録する**が、
報酬（referral_payouts）は作らない。判定を暗黙（list_id の有無など）に頼らず、
**予約の経路を明示するカラムを持つ**こと（例: booking_source 'list'|'delegate'|'direct'）。
暗黙判定は事故のもとになるため避ける。

### 16-22. 返金時は送金を自動停止する【2026-08-06・CEO最優先指示・実装済み】
完了後に返金が発生しても送金が止まらない穴を閉塞した（コミット 5e351e2）。
- **主軸**：送金実行の直前にStripeへ1回問い合わせ、返金（refunded / amount_refunded>0）または
  争議（disputed）を検知したら送金しない。`REFERRAL_STRIPE_WEBHOOK_SECRET` 未設定の
  現状でも動作する方式を選んだ
- **副軸**：`charge.refunded` / `charge.dispute.created` のwebhookハンドラも追加
  （シークレット登録後に有効化される）
- 検知時は referral_payouts を cancelled、referral_bookings.payment_status を refunded へ
- **送金済み後の返金は自動回収しない**（回収手段がないため）。note とCRITICALログのみ残す

### 16-24. 相談フォームのスパム対策【2026-08-06・CEO質問への回答と実装】

CEO質問「ボット対策、スパム対策はどうする？ワードプレスコメントみたいに攻撃される可能性アリ？」

**結論: ある。しかもWordPressのコメント欄より危険。**
このエンドポイントは認証なしで、**攻撃者が指定した任意のメールアドレスへメールを送れる**ため。
- ① メール中継として悪用される（第三者の宛先へ REAL PROOF の名前でメールが飛ぶ）
- ② 送信ドメインの評判が落ちる → **週次レポートなど他のメールまで迷惑メール行きになる**
- ③ プロの受信箱とダッシュボードがゴミで埋まる

②が一番痛い。相談フォーム1機能の問題では済まなくなる。

**実装した多層防御**（外部サービスを増やさない範囲）
| 層 | 内容 | 何を止めるか |
|---|---|---|
| ハニーポット | 画面に出ない入力欄。埋まっていたら機械 | 素直なボット |
| 滞在時間 | 描画から3秒未満の送信を弾く | 自動投稿スクリプト |
| リンク数 | 本文のURLが3本以上なら拒否 | コメントスパムの定型 |
| 同一ペア5分 | 同じメール×同じプロの連投 | 二度押し・軽い荒らし |
| メール単位 5件/時 | プロをまたいだ乱射 | **メール中継の悪用** |
| プロ単位 20件/時 | 特定のプロを狙い撃ち | 嫌がらせの物量 |

ボット確定（ハニーポット・滞在時間）のときは **200 を返して黙って捨てる**（検知を悟らせない）。

**未実装・将来の選択肢**: IPベースの制限（IPの保存が必要）、CAPTCHA（体験を損なうので最後の手段）、
Resend の送信ドメイン評判の監視。現状の防御を抜けてくる相手が出たら次を検討する。

### 16-27. 相談チャットの4点強化【2026-08-06・CEO指示・未着手】
参考にした構造：事前チャットで「会う前の不安」を下げ、予約に接続する型。
**優先度は現行タスクの後でよい**（CEO明言）。

**1. 返信期待値の設定**
スレッド上部に固定文言：「返信は施術の合間になるため、お時間をいただくことがあります」。
返信が来ない→不満、の連鎖を最初から断つ。クライアント側のやりとり画面
（`/consult/thread/[token]`）と、送信完了画面の両方に出すのが自然。

**2. 連投制限**
プロが返信するまで、クライアントの追送は**3通まで**。超えたら「返信をお待ちください」を表示。
実装メモ：`consultation_messages` を後ろから見て、最後の `sender='pro'` 以降の
`sender='client'` の件数で判定する（新カラム不要）。サーバー側でも弾くこと
（フロントだけだとAPI直叩きで抜ける）。

**3. 相談→予約の接続**
プロ側の返信画面に「このメニューを提案する」ボタン。選んだメニューがカードとして
スレッドに入り、クライアントはそこから予約リクエストへ進める。
相談で温まった人を、その場で予約に接続する。
実装メモ：メニューは `pro_menus`（`is_active` かつ `price_jpy > 0` かつ
`is_referral_bookable` の「予約可能なメニュー」定義に合わせる）。
スレッドへの入れ方は `consultation_messages` に構造化メッセージとして持つのが素直
（例：`sender='pro'` + 本文とは別に menu_id を持つカラム、または種別カラム）。
**§16-26 の予約ボタンと遷移先を揃えること**（将来どちらも内部予約システムへ差し替える）。

**4. 通報とプライバシー**
スレッドに通報ボタン。規約に
**「通常、運営はチャットを閲覧しません。通報があった場合のみ確認します」**を明記。
常時監視の息苦しさを避けつつ、記録が残る安心は担保する。
実装メモ：通報は別テーブル（`consultation_reports` 等）。通報された時点で運営が
閲覧できる状態にする。**この文言は規約とUIの両方に出す**（片方だけだと意味がない）。

### 16-28. チャットの定着そのものがバイパス対策になる【2026-08-06・CEO記録】
§16-12（紹介料のバイパス対策）との関連。

**プラットフォーム内チャットが定着すると「連絡はRPで」が既定になり、
外部連絡先の交換（＝離脱）の言い出しにくさが自然に生まれる。**

方針として明記する：**技術的なブロックではなく、チャットの利便性でバイパスを抑止する。**
外部連絡先の検出・マスキング・禁止といった規制的な手段は取らない
（いたちごっこになり、かつ正当なやりとりまで壊すため）。

この観点から、§16-27 の4点はいずれもバイパス抑止に効く：
- 1（期待値設定）と 2（連投制限）は、RP内のやりとりが「雑に流れない」状態を作る
- 3（メニュー提案）は、相談から予約までRP内で完結する導線そのもの
- 4（通報＋非閲覧の明記）は、RP内でやりとりする心理的安全性を上げる

### 16-29. 予約・紹介・相談を3つの独立した軸にする【2026-08-06・CEO決定・実装済み】
**§16-18（'conditional' で「紹介のみ停止」を表す）を置き換える。** 古い記述は残すが、以下が現行。

**変更の前提**: 直接予約システムを内製することが決まった（CEO決定）。
それに伴い「ホーム画面のトグル＝予約受付のイエス/ノー」であるべき、となった。

| 軸 | 保存先 | どこで切り替える | OFF で何が起きるか |
|---|---|---|---|
| **直接予約** | `professionals.booking_enabled` | ホーム上部のトグル | カードから予約ボタンが消える。代替リストがあれば代わりに案内 |
| **紹介予約** | `professionals.accepting_status`（open/closed） | 紹介タブ「紹介を受ける」先頭のスイッチ | 他のプロの紹介リストからの予約が止まる |
| **相談** | `professionals.consultation_enabled` | 相談タブ上部のスイッチ | カードから「相談する」が消える |

**なぜ2軸に割ったか**: `accepting_status` 1本では3状態しか表せず、
**「直接は止めるが紹介は受ける」が作れなかった**。2軸にすると4通り全部が表せる。

**'conditional' は役目を終えた。** 紹介の停止は `closed` で表す。
既存データに残っていても `computeReferralSignal` / `isAcceptingOpen` は closed と同じ扱いなので実害はない。

**代替リストの判定軸が変わった（重要）**:
公開カードの代替リスト案内は `accepting_status` ではなく **`booking_enabled`** で出す。
訪問者にとっての行き止まりは「予約できないこと」であって、プロ同士の紹介ネットワークの
状態ではないため。`computeReferralSignal` はプロ向け検索・ピン追加の判定には
`accepting_status` のまま使う（こちらは紹介ネットワークの軸）。

### 16-31. 投票画面のプレビュー導線【2026-08-06・CEO指摘・実装済み】
「プロはクライアントに見せる画面を確認したい。これを分かりやすくしたい」。

**QRコードの下の文字リンクに移した**（旧: ページ最下部のフルサイズボタン）。

  2つの小リンクにした（どちらもQRまわりの小操作で性質が揃っている）

### 16-32. オススメのプロを専用ページに出す【2026-08-06・CEO決定・実装済み】
**§16-8 / §16-14 の「公開カードに代理案内の候補ブロックを出す」を置き換える。**

**事故**: カードのヘッダー内（狭いフレックス枠）に候補一覧を押し込んだ結果、
**文字が縦書きに潰れて完全に壊れた**（CEO報告「ぶっこわれた」）。

**決定**: **公開カードにリストは載せない。**
- カードに出すのは **1行だけ**：「◯◯さんは今ご予約を受け付けていません」
  （「同じ◯◯の先生をご案内します」は長すぎるとのCEO指摘で削除）
- **予約ボタンの位置に「オススメのプロ」ボタン**を出す（候補が1名以上いるときだけ。
  押した先が空だと行き止まりになるため）
- 一覧は専用ページ **`/recommended/[id]`** に出す。幅の制約が無いので表示が壊れない
- ページ先頭に根拠を書く：「◯◯さんと同じ強み『△△』を持つ、□□の先生です」

**クライアント向けの文言から内部用語を排除**：「代替リスト」「代理案内」は使わない。

### 16-33. 本人にプルーフが無い場合の案内【2026-08-06・CEO質問への回答・実装済み】
CEO質問「団体トップがプルーフを集めてない場合、どうしようか？」

**旧実装は `return null` で案内そのものが消えていた**（本人の評価済み強みが0件だと打ち切り）。
これは行き止まりを作らないという目的に反する。

**決定：強みでの絞り込みをやめ、同じ団体の受付中の先生をそのまま案内する。**
強みの一致は「あれば加点」であって前提ではない。

**文言は根拠に応じて自動的に落とす（言えることだけ言う）**:
| 本人の強み | ページ先頭の文 |
|---|---|
| あり | 「◯◯さんと同じ強み『△△』を持つ、□□の先生です」 |
| なし | 「◯◯さんと同じ□□に所属する先生です」 |
| 自作リスト | 「◯◯さんが信頼している先生です」 |

持っていない根拠を語らない。これが守れていれば、プルーフが無い代表でも嘘にならない。

### 16-34 / 16-35. 公開カードの一覧掲載をやめ、紹介はチャットから手渡す【2026-08-06・CEO決定】
**§16-8 / §16-14 / §16-32 の「停止中プロの公開カードに候補一覧を出す」を大きく制限する。**

**CEOの指摘（これが本質）**:
> 代理案内とか代替リストをフロントで出しちゃうと、そもそも紹介につながらない！！

**なぜ致命的か**: 公開カードに一覧が並ぶと、クライアントはそこから勝手に選ぶ。
その着地は「**誰の紹介でもない**」。紹介の実体が無く、送り手の記録も残らず、
「誰の信頼を経由して来たか」（§16-21で受け手に見せると決めたもの）も失われる。
一覧を出すほど紹介機能が空洞化する、という自己矛盾になっていた。

#### 16-34. 公開カードに一覧を出せるのは団体オーナーだけ
- `organizations.owner_id = professionals.user_id` のプロのみ、候補一覧を算出・掲載する
- 団体オーナーは「自分の団体の認定者へ流す」という立場が明確で、
  かつ団体名が保証として機能するため例外とする
- それ以外のプロのカードでは候補を一切算出しない（クエリも投げない）

#### 16-35. 紹介は相談チャットからワンクリックで手渡す
オーナー以外が人を回したいときの正規ルート。
- プロ側の相談スレッドに **「紹介リストを送る」** ボタン。共有可能なリスト（private以外・slugあり）から選ぶ
- クライアントのスレッドに **「◯◯さんからのご紹介」カード**が入り、「紹介された先生を見る」で `/r/[slug]` へ
- **これは「◯◯さんが紹介した」という実体が残る**。フロント掲載には無かった価値がこれ
- migration 054: `consultation_messages.list_id`（menu_id と同じ作り・body に人が読む文を必ず入れるので
  カラムが無い環境でも会話は成立する）

**この設計は §16-28（チャットの利便性でバイパスを抑止する）とも噛み合う。**
紹介がチャットの中で完結するほど、RP内でやりとりする理由が増える。

### 16-36. 送信の取り消し（プロ・クライアント両方）【2026-08-06・CEO決定】
**CEOの指摘**:
> ワンタップでリストが送られてしまうのでミスが多くなりそう。送信取り消しの仕組みも作って。

その後、消し方について明確な決定が出た:
> 相手の画面からも消えるけどシステムには残る、とするべき。そもそも削除の目的は
> 相手に送ったメールを消すこと。**ヤバイことを送るやつが自分でヤバイと思って取り消すなら、
> 運営が間に入る手間が減るだけ。だれかを捕まえるのが目的ではない。**
> その上で、いざというときのためにシステムにはメッセージを残しておく。

#### 決定した仕様
- **どちらの画面からも消える**（プロ側／クライアント側の両方）。片方に残ると「消したのに見えている」になる
- **行は残す**（`consultation_messages.withdrawn_at` を立てる論理削除・migration 055）。
  通報が来たときに運営が確認できる約束（§16-27-4）を守るため
- **取り消せるのは自分の発言だけ**。プロは `sender='pro'`、クライアントは `sender='client'`
- **クライアント側にも用意する**（CEO問い「クライアントも送信取り消し出きるようにすべき？」への回答）。
  誤送信は相談する側にも起きるし、片側だけ取り消せるのは対等でない
- **メールは取り消せない**。確認ダイアログで必ずそう書く
  （「やりとり画面からは消えますが、相手に届いたメールは取り消せません」）。
  取り消した＝相手は見ていない、と誤解させないため

#### 連投制限との関係（重要）
§16-27-2 の連投カウントは **取り消し済みも数に入れたまま**にする。
除くと「3通送る → 取り消す → また3通送れる」で制限を素通りできる。
表示は取り消し後、カウントは取り消し前。ここを揃えてはいけない。

#### fail-soft
migration 055 未実行の環境では `withdrawn_at` の UPDATE が失敗する。
そのときだけ従来どおり**物理削除**にフォールバックする（CEO「物理削除でok」）。
取り消せないまま誤送信が残り続けるほうが害が大きいという判断。

### 16-41. 完了時のプルーフ依頼は自動送信しない【2026-08-08・CEO決定】
D-2調査で「完了時にクライアントへプルーフ依頼が送られない」ことが判明し、CCは
完了時の自動送信を提案したが、**CEOがこれを却下**。理由は2つ:
1. **メールで送ると記入率は圧倒的に下がる**（対面のその場タップと比べて）
2. **「プロが結果を出せたときに任意で提示する」という思想に反する**。
   完了と同時に機械的に送るのは、記録の意味（プロが自信を持って依頼する）を壊す。

#### 決定した方向
- **プロが後から任意のタイミングで送れる**依頼ボタンを設ける（完了済み予約から）。
- 単なる送信機能ではなく**「書かせる施策」とセット**で設計する（記入率対策が本体）。
- 対面QRは従来どおり最強の導線として残す。オンライン依頼はその補完。
- ※トップ改修（§16-40）ヒーローUSP「使うほど貯まる」の成立条件は、
  「自動で貯まる」ではなく「**貯める手段が予約フローに組み込まれている**」と再定義。

#### 実装GO（2026-08-08・CEO）＋リンク方式の指定
- **メールのリンクはQRと同じトークン式**（`/vote/{プロID}?token=...`）にする。

- 派生対応: `qr_tokens` に `booking_id` 列を追加（migration 061）。ダッシュボードの

#### 予約経由の記録は本人確認もスキップ【2026-08-08・CEO決定】
- CEO:「予約からの投票は認証不要。すでにメールアドレスと電話番号もらってるから二度手間」。

  合理性: **予約のメール宛に届いたリンクを開けた＝そのメールの持ち主**（マジックリンクと同じ）。
  本人性は予約時点＋リンク到達で担保済みであり、6桁コードは純粋な二度手間。
- 実装: booking_id 付きトークンで来た場合のみ、authステップを飛ばし新API
  `/api/vote-auth/booking-confirm` がサーバー側で token→予約→client_email を解決して確定。
  **client_email はブラウザに一切降ろさない**。店頭QR（booking_id null）は従来どおり本人確認あり。
- 残る保護（スキップ後も全て有効）: トークン1回使い切り(used_at)・72h期限・重複投票チェック・
  30分クールダウン・自演ブロック（送信時/QR発行時の self_request 拒否＋確定時の self_vote 拒否）・
  visit_claim による proof/continuation 判定。
- **既知のトレードオフ（レビュー指摘・記録）**: 依頼トークンのURL/QRは受け手プロ自身の画面に
  表示されるため、認証ゲートが無い以上、**プロが自分の端末でクライアント名義の記録を完了する
  ことが技術的には可能**（1予約1回・予約実在が前提の範囲で）。二度手間の解消と引き換えに
  受け入れた整合性コスト。将来の緩和候補: 記録の「認証レベル」列で表示/集計を重み付け、
  QR/URLをプロ画面に出さずメールのみに閉じる、等。悪用の兆候（不自然な即時記録の多発等）が
  出たら再検討する。

### 17-1. 直接予約（紹介元なし・予約金なし）【2026-08-06・CEO決定】
**CEOの指示**:

| サービス | 起きている失敗 | 今回の設計での潰し方 |

#### 実装方針: 新しい予約テーブルを作らない
紹介予約(`referral_bookings`)をそのまま使い、**違いは2つだけ**にする。
- 紹介元がいない → `list_id` / `sender_pro_id` は null
- 予約金がない → Stripe を一切通らない（`payment_status='not_required'`・`fee_*_bps=0`）

これで受け手側の**確定 / 辞退 / 別日時の提案 / 日時変更 / キャンセル / 完了 / 48h失効cron / 自動完了**が
すべて既存のまま効く。新しく作ったのは入口（フォームとAPI）だけ。
`referral_bookings.source='direct'` は**文言の出し分けのためだけ**に持つ
（紹介元がいないのに「紹介予約が確定しました」と書くと意味が通らないため）。

#### 予約の受け方は必ず1本（`professionals.booking_mode`）
| 値 | 挙動 |
|---|---|
| `'rp'` | 公開カードの「予約する」→ `/book/[proId]`（REALPROOFで受ける） |
| `'external'` | `booking_url` へ（本人のサイトで受ける）。RPには予約が届かない |
| `null`（未選択） | `booking_url` があれば external、無ければ rp |

判定は `src/lib/booking-mode.ts` の `resolveBookingTarget()` に集約する（公開カード・相談チャット・
予約ページが同じ関数を見る）。未選択の解釈を入れてあるのは、**今まで自分のサイトを予約ボタンに
設定していた人の挙動を、本人が選ぶまで変えない**ため。

#### メニューからの予約は必ずREALPROOF（CEOの問いへの回答）
「こちらは必ずrpネイティブでいいかな？」→ **はい**。理由は、外部サイトに「このメニューで」を
渡す手段が無く、飛ばした瞬間にお客さんが選んだメニューが消えるため。
- 出すのはプロが「このメニューで予約を受ける」(`pro_menus.is_referral_bookable`)を
  ONにしたメニューだけ。**これが「自分のサイトで受けたい人」の逃げ道**になる（スイッチを切れば導線ごと消える）
- 遷移先は `/book/[proId]?menu=<menu_id>`。メニューを持ったままフォームに入る
- 相談チャットのメニューカード「このメニューで予約に進む」も同じURLへ統一（§16-27-3の暫定リンクを差し替え）

#### 予約可能メニューの定義が紹介予約と違う点
紹介予約は `price_jpy > 0` を要求する（0円だとオンライン決済を素通りできてしまうため）。
直接予約は**オンライン決済が存在しない**ので、この制約を置かない。0円メニュー（初回相談無料など）も予約できる。

#### フォームは1つ（`ReferralRequestForm` の `variant='direct'`）
別フォームを作らない。日時ピッカー・進行順・受付時間の警告・過去日時ブロックがまったく同じで、
コピーすると必ず片方だけ直る状態になるため（CLAUDE.md §G）。variantで変えるのは
「送信先API」「予約金の説明を出さない」「同意文」の3点だけ。

#### 受信箱は1つ
直接予約も紹介予約も同じ「予約を受ける」タブに届く（旧「紹介を受ける」から改称）。
プロから見て「予約が届いた」は1つの概念であり、置き場所を分けると片方を見落とす。
どこから来たかはカード内の1行（`REALPROOFからのご予約` / `紹介元: ◯◯さん`）で示す。

#### migration 056
- `professionals.booking_mode text`（DEFAULTなし）
- `referral_bookings.source text`（DEFAULTなし）
未実行でも動くように fail-soft を入れてある（source無しで INSERT し直す／booking_mode は別クエリで読む）。
ただし**未実行の間は「自分のサイトで受ける」の選択が保存されない**。

### 17-2. 予約と紹介をメニューごと分ける【2026-08-06・CEO判断】
**CEOの指摘**:
> ここの上の通知は「対応中の予約」とするべき。紹介予約だけじゃなくなったから。
> それと、通常予約も紹介メニューに入ってるのがおかしい。予約メニューにして、紹介をいれるか？
> だとしたら、予約設定もこのなか？ というか、そうすると紹介が目立たなくなるのもデメリット。
> 紹介を本丸の機能としたのに。

**決定: 予約と紹介を別のトップレベルメニューにする。**

| メニュー | 中身 | 性質 |
|---|---|---|
| 予約 | 受信箱（直接予約＋紹介予約）／予約の受け方・メニュー設定への導線 | **受け取る仕事**・毎日 |
| 紹介 | 紹介する（リスト作成・送信）／紹介した案件／紹介予約の受付スイッチ | **送り出す仕事**・ときどき |

**「紹介が目立たなくなる」への答え**: 逆になる。分ける前は、紹介タブを開くと最初に出るのが
受信箱で、紹介の本丸（リストを作る・送る）は2番目のサブタブに隠れていた。
分けたことで紹介タブ＝紹介する場所になり、先頭に出る。

**受け口は1つのまま**。直接予約も紹介予約も同じ受信箱に届く（§17-1の原則を崩さない）。
どこから来たかはカード内の1行（`REALPROOFからのご予約` / `紹介元: ◯◯さん`）で示すので、
紹介の存在感は予約タブの中にも残る。

**波及して直したもの**
- ダッシュボード上部の1行バナー: 「対応中の**紹介**予約が2件」→「対応中の**予約**が2件」
  （送り手側の「紹介した案件が◯件」はそのまま。こちらは紹介で正しい）
- 受け手プロ宛の通知メール/LINEのリンク先: `?tab=referral` → `?tab=bookings`
  （予約リクエスト・逆指定の承諾・日時変更の確定）
- 古いリンク `?tab=referral&sub=receive` は404にせず「紹介する」に着地させる

### 17-3. メールアドレスの打ち間違い対策【2026-08-06・CEO指摘】
**CEOの指摘**:
> 予約リクエスト、クライアントがe-mailを誤って入力していたらどうする？
> クライアントはなんも通知なくて、プロには予約が入ってる、が起こりうる。

予約でいちばん重い事故。お客さんは「送ったのに音沙汰がない」、プロは枠を空けて待つ。
**しかも両者とも気づかない**。1つの対策では防げないので、4段で受ける。

| 段 | 対策 | 効く相手 |
|---|---|---|
| ① 入力時 | よくあるドメインの打ち間違いを検出して「もしかして◯◯？」（タップで修正）。`src/lib/email-typo.ts` | gmial.com / yahoo.co.jp の綴り違いなど |
| ② 送信直前 | 「お返事の届け先」としてアドレスを大きく再掲し、本人に読ませる | 全角・別アドレスの取り違え |
| ③ 送信直後 | 受付メールの送信結果(`receipt_sent`)を完了画面で伝える。失敗なら赤く出す | 形式は正しいが Resend が弾いた宛先 |
| ④ 事後 | 送信に失敗した予約は、プロのカードに「お客さんに受付メールが届いていません。確定したらお電話でも」と出す | 上記をすり抜けた場合の最後の砦 |

**電話番号が必須項目であることが効いている**。メールが死んでも連絡手段が1つ残る。
④はその手段をプロに使わせるための表示。

**やらなかったこと**: バウンス（送信は成功したが後から宛先不明で戻る）の検知。
Resend の webhook 受け口が必要で、今回のスコープ外。存在しないドメインではなく
**存在するが本人のものではないアドレス**（打ち間違いで他人に届く）はどの段でも防げない。

### 17-4. 電話で決めた予約をプロ側から確定する【2026-08-06・CEO指示】
**CEOの指示**:
> そんで電話で口頭で予約確定したら、プロ側でも予約確定出来るようにする。
> ボタンを押すと警告画面をだしながら。

§17-3の④（受付メールが届かなかった場合の逃げ道）と対になる機能。
メールアドレスが誤っていると、お客さんはRPの画面に戻ってこられない。
それでも電話が通じれば予約は成立させられる。**そこを行き止まりにしない。**

- action: `confirm_offline`（`PATCH /api/referral/bookings/received`）
- **お客さんが出した3つの希望日時に縛られない**。電話で話した結果は別の日時になることのほうが多い
- 実行前に必ず警告（window.confirm）:
  - お客さまの画面上の同意なしに確定すること
  - 確認メールは送るが、アドレスが誤っていれば届かないこと
  - 日時の取り違えがあっても REAL PROOF では確認できないこと
- 記録: `preferred_slots.confirmed_by_phone_at`。確定済みカードに
  **「お電話で確定した予約です」**を常時表示する（当日の行き違いを防ぐ）
- 日時は `preferred_slots.confirmed_slot_iso` に入れる。以後の日時変更・
  カレンダー・キャンセル判定はすべて既存の `resolveConfirmedSlotIso` が拾う
- **予約金の決済が必要な紹介予約では使えない**（409 `payment_required`）。
  支払いを飛ばして成立させられる穴になるため

### 17-5. 受付スイッチを「予約」タブに集約【2026-08-06・CEO判断】
**CEOの問い**: 紹介予約受付のトグルは予約メニューに移す？ 設定メニューに移して予約タブに一言足す？

**決定: 予約タブへ移す。**
- 紹介予約の受付は「**受け取るか**」の設定であって、紹介する仕事ではない（§17-2と同じ理屈）
- 受付スイッチが画面をまたいで散らばると、「今日は止めたい」人が探し回ることになる。
  予約に関わる2つ（直接予約・紹介からの予約）は1画面で止められること
- 設定メニューは「たまに触るもの」の置き場。受付は毎日触りうるので設定の奥に埋めない

結果:
| 場所 | 何を止められるか |
|---|---|
| ホーム上部のトグル | 直接予約（よく使うので近道として残す） |
| 予約タブ ヘッダー行 | 直接予約 |
| 予約タブ 本文先頭 | 紹介からの予約 |
| 相談タブ 先頭 | 相談 |

紹介タブには行き先の1行だけ残す（今まで触っていた人が迷子にならないように）。

### 17-6. 予約のやりとりは REAL PROOF の中で（メールアドレスを出さない）【2026-08-06・CEO指示】
**CEOの指示**:
> 直接予約、紹介予約問わず、クライアントのメールは表示せずに、リアプルの相談チャットにリンクして欲しい。

**なぜ**: メールアドレスを出した瞬間に、やりとりが REAL PROOF の外へ出る。
記録も、通報の受け口も、次の紹介への接続も消える（§16-30「リードはこっちで握る」と同じ線）。

**仕様**
- 予約カードの連絡先ブロックから**メールアドレスの表示をやめる**
- 代わりに「**メッセージを送る**」→ `POST /api/pro/bookings/[id]/thread` → 相談タブへ
- **電話は残す**。当日の連絡手段であり、メールが死んでいる場合の唯一の手段でもある（§17-3④）
- 新しいテーブルは作らない。**既存の相談スレッド(consultations)を再利用**する
  - 同じプロ × 同じメールアドレスのスレッドがあればそれを返す
    （予約ごとに別スレッドを作ると、同じお客さんとの会話が分断される）
  - 無ければ空のスレッドを作る。お客さんへの通知はプロが最初の1通を書いた時点で飛ぶ
    （既存の返信フローがそのまま送る。作成時点では何も送らない）
  - アーカイブ済みなら受信箱へ戻す（プロが今まさに使おうとしているため）
- 開示条件は既存のまま（confirmed / completed のみ）

**同時に直したもの（CEO報告）**
- 確定済みカードに**相談内容（メニュー・テーマ・補足）が出ていなかった**。当日に向けて
  一番読みたい情報なので、確定後こそ出す
- 確定済みカードの見出しが `client_nickname` 固定で、直接予約では「ご相談者さん」に
  なっていた。開示条件を満たしていれば**本人が入力した名前**を出す
- 直接予約に**案件スレッド・引き継ぎメモ**を出さない。どちらも紹介元のプロと
  やりとりするための道具で、紹介元がいない予約では相手が存在しない

### 17-7. バウンス検知（§17-3の穴を塞ぐ）【2026-08-06・CEO報告】
**CEO報告**:
> 予約フォームで間違ったメールを登録してみたけど、プロ側には電話して下さいが表示されない。

**なぜ出なかったか**: §17-3で「対象外」と書いていた層そのもの。
打ち間違いでも**形式が正しく、ドメインが実在する**（gmail.com など）と Resend は受理して成功を返す。
宛先不明が分かるのは数秒〜数分後の**バウンス通知**で、これは非同期。
送信APIの戻り値だけを見ている限り、この層は**絶対に検知できない**。

**対処**: `POST /api/webhooks/resend` を追加。`email.bounced` を受け取り、そのアドレス宛の
進行中の予約（requested / confirmed）に `preferred_slots.receipt_email_failed` を立てる
→ プロのカードに「お客さんに受付メールが届いていません。お電話でご連絡をお願いします」が出る。

**有効化には Resend 側の設定が要る（CEO作業）**:
1. Resend ＞ Webhooks ＞ Add Endpoint / URL: `https://realproof.jp/api/webhooks/resend` /
   イベント: `email.bounced`
2. 表示された Signing Secret（`whsec_...`）を Vercel の環境変数 `RESEND_WEBHOOK_SECRET` に設定

未設定の間はエンドポイントは何もしない（署名を検証できないものは受け付けない）。
署名は Svix 形式（`svix-id` / `svix-timestamp` / `svix-signature`）を HMAC-SHA256 で検証し、
5分より古いものは弾く。

### 17-8. 相談チャットのバウンス表示とやりとりの削除【2026-08-06・CEO指示】
**CEOの指示**:
> 同じ仕組みは相談チャットにも入ってる？ 相談チャットの場合は、クライアントが返信手段が
> ないとなにも無いので、それをチャット内に表示してワンクリックでチャットを消去できるようにして。

**相談のほうが重い理由**: 予約には**電話番号**がある（§17-3④はそこへ逃がす）。
相談は**メールしか預かっていない**。届かない＝クライアントはやりとり画面に戻る手段が一切ない。
プロが返信を書き続けても永久に届かないので、その事実を出して畳めるようにする。

- `POST /api/webhooks/resend` が `email.bounced` を受けたとき、予約に加えて
  **相談スレッドにも印を立てる**（`consultations.email_failed_at`・migration 058）
- 相談タブ:
  - 一覧の見出しに「**メール届かず**」（開かなくても分かる＝返信を書く前に気づける）
  - スレッドを開くと赤いブロックで理由を出し、「**このやりとりを削除する**」を1クリック
- 削除は**行ごと消す**（`consultation_messages` → `consultations`）。
  §16-36（メッセージの取り消し＝論理削除）とは扱いを変えている。
  理由: 取り消しは「相手に届いたものを引っ込める」＝相手が存在する。
  こちらは**相手に何も届いていないスレッドの後始末**で、残しても誰の役にも立たない。

**migration 058 未実行の間**: webhook も API も fail-soft で素通りする（相談機能は普通に動く）。
ただし「メール届かず」の表示は出ない。

### 17-9. メールが届かない予約は、プロ側で完結できるようにする【2026-08-06・CEO指示】
**CEOの指摘**:
> アドレス間違いの可能性のメッセージは出た。だけど、確定前に電話番号を出すべきでは？
> プロが確定しないと電話番号が出ない。
> また、その場合に限り、予約の削除、確定日付の変更などプロ側で出来るようにすべき。
> そして、メールが届いてないクライアントはもちろんチャットも使えないから、
> メッセージを送るも表示しないで。

**何が詰んでいたか**: 連絡先の開示は「確定後」が既定（§2-4ステージ3）。
ところがメールが死んでいる予約では、**確定の連絡を取る手段が電話しかないのに、
確定するまで電話番号が出ない**。順序が逆立ちしていた。

**メールが届いていない予約に限り**（`preferred_slots.receipt_email_failed`）:
| 変えたこと | 理由 |
|---|---|
| **確定前(requested)でも連絡先を開示** | 確定の相談を電話でするしかないため。出すのは**お名前と電話番号だけ** |
| **「メッセージを送る」を出さない** | チャットの通知もメールで飛ぶ。押せるだけ無駄 |
| **確定済みでも日時をその場で差し替えられる**（`confirm_offline` を confirmed にも許可） | 通常の日時変更は「提案 → クライアントが承諾」だが、提案が届かない |
| **「この予約を削除する」**（`action: 'discard'`） | 通常のキャンセルと分ける: ①クライアントへ通知しない（送ってもbounceを増やすだけ）②返金判定を通さない（予約金が動いている予約は通常のキャンセルへ誘導） |

削除は**行を消さずキャンセル扱い**にする。予約は金額・完了・自動完了cronが絡むため、
相談スレッド（§17-8）のような行ごとの削除はしない。

**あわせて**: `client_contact` から `email` をレスポンスごと落とした（§17-6で画面から消したが、
開発者ツールでは見えていた）。プロ側にクライアントのメールアドレスを渡す経路はこれで無くなった。

#### 17-9 補足: 予約金がある場合【CEO質問 2026-08-06「予約金がある場合は？」】
| 予約の種類 | 予約金 | メール未達のときにできること |
|---|---|---|
| 直接予約（§17-1） | **常に無し**（構造上ゼロ） | 電話 → 日時を直す → 削除。すべて使える |
| 紹介予約・決済フラグOFF | 無し | 同上 |
| 紹介予約・未払い（`unpaid`・確定前） | これから発生 | 削除は可（お金はまだ動いていない）。**電話での確定は不可**（支払いを飛ばして成立させられるため。通常の確定＝決済リンク送付へ誘導） |
| 紹介予約・支払い済み/待ち（`paid`/`awaiting`） | 動いている | **削除を出さない**。返金の判定が要るので通常のキャンセルへ。この場合だけ「変更・キャンセルなどの操作」を**隠さない**（逃げ道を塞がないため） |

**危なかった点**: §17-9で「変更・キャンセルなどの操作」を丸ごと隠したため、
予約金ありのケースで「削除は使えません→通常のキャンセルをどうぞ」と案内しながら、
その通常のキャンセルが画面に無い状態になっていた。CEOの質問で発覚。
**逃げ道を塞ぐ非表示は、塞いだ先に道があるかを必ず確認する。**

なお `isReferralPaymentEnabled()` は `REFERRAL_STRIPE_SECRET_KEY` の有無で決まる。
本番未投入の間はどの予約にも予約金は発生しない（Stripe本番化4点セットは未着手）。

### 17-10. メールアドレスを直して送り直す【2026-08-06・CEO指示】
**CEOの指示**:
> 紹介予約の場合は、正しいメールアドレスを確認して入力させるようにしないと、
> クライアントに予約金の支払いメールを送れない。プロには電話でメールを確認させて。
> そんでメールアドレス修正のボックスをだす。

紹介予約は**予約金の支払い案内が届かないと予約が成立しない**。相談や直接予約と違い、
「電話で話がついた」だけでは終われない（お金の導線がメールにしかない）。

- 予約カードに「**メールアドレスを直す**」→ 入力 → 保存すると**ご案内を送り直す**
- 送り直す中身は状況で変わる:
  | 状況 | 送り直すもの |
  |---|---|
  | 確定済み・予約金が未払い | **予約金の支払いリンク**（`issueFeePaymentLinkAndNotify` を再実行） |
  | 確定前 | 受付メール |
  | 確定済み・予約金なし | 確定のお知らせ |
- 保存時に `receipt_email_failed` を下ろす。それでも届かなければ webhook がまた立てる

**フォールバックが要る**（そのまま渡し切りにはできない）:

|---|---|---|
| 通知 | LINE/メールで「要対応」（電話番号は入れない） | なし |
| 画面 | 「紹介した案件」に赤ブロック・電話ボタン・アドレス修正 | 「紹介元の◯◯さんが確認しています」だけ |
| 24時間経過後 | 消える | 従来の操作一式が出る |

①メール未達 ②進行中 ③自分が担当期間内、の3つが揃うときだけ**お名前と電話番号**を返す。
通知本文には番号を入れない（メール/LINEは転送・スクショで簡単に外へ出る）。

#### 同時に直した不具合（CEO報告「電話番号が表示されてない」）
`canDiscloseContact()` のメール未達の例外を **requested にだけ**効かせていたため、

### 17-18. 「Voiceが保存できない → 何回か試したら通った」の真因【2026-08-06・CEO報告】

画面に出た **"Unauthorized"** は API の `auth()` が userId を取れなかった 401。

**真因**: Clerk のセッショントークンは**短命（約60秒）**で、クライアントのタイマーが黙って
更新し続けている。スマホでタブを開いたまま放置する・画面を消す・別アプリに切り替えると、
この更新タイマーが止まる。復帰後の**最初の1回**は期限切れのまま飛ぶので 401 になり、
その後 Clerk が更新するので**2回目以降は普通に通る**。
データにもコードにも問題は無く、「久しぶりに操作した最初の1回だけ落ちる」という形で出る。

**対処**（`src/lib/fetch-with-session-retry.ts`）:
- 401 なら `getToken({ skipCache: true })` でセッションを取り直し、**黙って1回だけ再送**する
- それでも駄目なら、英語の "Unauthorized" ではなく日本語で伝える（入力内容は残す）

※ いまは Voice の返信（保存・削除）に適用済み。**他のダッシュボード操作も同じ経路で
起こりうる**ので、報告があった順に同じヘルパーへ寄せる。

### 17-19. SMS（予備の到達手段）と、人力フローの撤去【2026-08-06・CEO指示】

**CEOの指示**: 「予備でsmsは入れておきたい」「これを登録したら、既存のプロに電話させる流れも削除したい」

**なぜ要るか**: メールは「送れたのに届かない」ことがある（打ち間違い・迷惑メール判定・キャリア遮断）。
そのとき**予約金の支払い案内が一切届かず、予約が成立しない**。
電話番号は予約フォームの必須項目なので、SMSなら必ず1本は道が残る。

**§17-16 の人力フローとの関係（CEOの質問「smsがあれば上記のわずらわしいやりとりはいらない？」への答え）**

ほぼその通り。ただし**消すのではなく降格させる**。
```
バウンス検知
  ├─ SMS送信に成功 → contact_recovered_by_sms_at を立てて終わり
  │                    プロ側には何も出さない（電話させない）
  └─ SMS送信に失敗 → 従来どおり §17-16 の人力フロー
      （＝電話番号まで間違っている。ここは人が動くしかない）
```
判定は `resolveEmailFixOwner()` 1か所。`contactRecoveredBySms` が真なら null を返すので、
送り手・受け手どちらの画面からも対応ブロックが消える。

**未設定の間は何も変わらない**: `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` / `TWILIO_SMS_FROM` が
揃わないと `sendSms()` は必ず false を返す（決済の `isReferralPaymentEnabled` と同じ作法）。
3つ揃った瞬間に自動で切り替わる。

**実装** (`src/lib/sms.ts`)
- Twilio SDK は入れず REST を fetch で叩く（依存を増やさない・チャンクグラフに重いものを持ち込まない）
- `toE164Jp()`: `090-1234-5678` 等の国内表記を `+81...` に直す。
  **携帯(070/080/090)以外は送らない**（固定電話にSMSは届かない）
- エラー本文には宛先番号が含まれうるのでログに出さない（status のみ）

**本文の原則**
- **PIIを書かない**。名前も金額も日時も書かず、短いリンクだけ
  （SMSは家族と共有の端末で見られることがある）
- リンク先は `/booking/[id]`。支払いボタンも状況表示も既にあるので、
  requested / confirmed / 支払い待ち を1本のリンクで賄える

**取引と販促は混ぜない**（CEOの「電話番号で登録したプロにもリワードを送ったり連絡できる」への注記）
- 支払い案内・リマインド = **取引**。番号を預かった目的そのものなので送ってよい
- リワード案内・新機能のお知らせ = **販促**。同意なしに送るとクレームとブロックが一気に来る
  （メールと違って逃げ場がないので体感が強い）
- 販促SMSを始めるときは、**明示的なオプトインを先に作る**

**今後の送信タイミング**（未実装）
| タイミング | 理由 |
|---|---|
| 支払いリンクを出して数時間、未払い・未開封 | バウンスしない不達（迷惑メール・キャリア遮断）はこれでしか拾えない。件数はバウンスより多いはず |
| 前日リマインド | ノーショー対策。件数が少なく効果が大きい |

全予約には送らない。コストもだが、通知チャネルは使い減りする。

### 17-20. 相談チャットのメールが別のメールボックスへ飛んでいた【2026-08-06・CEO報告・本番不具合】

**CEO報告**: 「予約カードでプロから始める相談チャットは機能しないよ。クライアントにメールがいかない。」

**真因**: `consultations.client_email` に **`normalizeEmail()` を通した値**を保存していた。
`normalizeEmail()` は重複チェック用の**照合キー**を作る関数で、

- 全ドメインで `+タグ` 以降を落とす（`foo+test@example.com` → `foo@example.com`）
- Gmail はさらにドットも落とす

つまり `foo+test@example.com` に送ったつもりのメールが `foo@example.com` という
**別のメールボックス**へ飛んでいた。Gmailのドットだけなら偶然届くので、
「ときどき届く／ときどき届かない」に見える。

CLAUDE.md には **「検索・重複チェックは `normalized_email`、`voter_email` は表示用」**と
書いてあり、`referral_bookings` は正しく生アドレスを保存していた。
`consultations` だけがこの線を踏み越えていた（プロ発の予約スレッドも同じ関数を踏襲していた）。

**同じ根の2つ目**: バウンス webhook も逆向きに壊れていた。
バウンス通知は**生アドレス**で来るのに、`normalizeEmail()` に畳んでから
`referral_bookings.client_email`（生アドレス保存）を `.in()` で探していた。
`+タグ` 付きのアドレスでは**永久に一致せず、予約に「届いていない」印が立たなかった**。

**修正**:
| 場所 | 保存 | 照合 |
|---|---|---|
| `POST /api/consultations` | **生アドレス**（trim+lowercase） | JS側で両辺を正規化して比較 |
| `POST /api/pro/bookings/[id]/thread` | **生アドレス** | 同上 |
| `POST /api/webhooks/resend` | — | **生と正規化の両方**で `.in()` |

**線引き（今後これを踏まない）**:
> **正規化したアドレスは「同じ人か」を判定するためのキー。宛先ではない。**
> 送信・表示に使う値は、必ず本人が入力したものを保存する。

**既存行について**: すでに正規化後の値で保存された相談スレッドは、生アドレスが
どこにも残っていないため復元できない（`+タグ` を使っていた人だけが対象）。
新規ぶんは上の修正で正しくなる。
