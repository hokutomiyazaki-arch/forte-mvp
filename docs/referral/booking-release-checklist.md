# 予約システム 通しテスト（本番・2026-08-06 リリース分）

CC は realproof.jp に到達できない（ネットワークポリシーで403）。**実機での確認は CEO 側**。
所要 10〜15分。**告知を送る前に**これを1周してほしい（今日作ったばかりの導線のため）。

順番に押していけば終わる形にしてある。詰まったところの画面を送ってもらえれば直す。

---

## A. プロ側の準備（2分）

- [ ] メニュー ＞ **サービス設定 ＞ 予約の受け方** に「REALPROOF で受け取る／自分のサイトで受け取る」が出る
- [ ] 「REALPROOF で受け取る」を選んで保存 → 保存後にもう一度開いて**選択が残っている**（migration 056 が効いている確認）
- [ ] サービス設定のメニューを1つ、「紹介・予約を受け付ける」ON・料金あり にしておく
- [ ] ホーム上部のトグルが **予約 受付中** になっている

## B. お客さん側（別ブラウザ／シークレットで・3分）

- [ ] `/card/<自分のID>` を開く → **予約する** が出る（押すと `/book/<自分のID>` へ）
- [ ] サービス・案内タブのメニューに **このメニューで予約する** が出る → 押すと予約フォームでそのメニューが選択済み
- [ ] メールアドレスに `test@gmial.com` と入れる → **「もしかして test@gmail.com ですか？」** が出る（タップで直る）
- [ ] 送信の直前に「**お返事の届け先**」としてアドレスが再掲される
- [ ] 希望日時を1〜3つ、名前・電話・メールを入れて送信 → 完了画面に
      「受付メールをお送りしました」＋**ご予約の状況を見る**ボタン
- [ ] 受付メールが届く（届かなければ迷惑メールも確認）

## C. プロ側で受け取る（3分）

- [ ] メール or LINE に「**予約のリクエストが届いています**」が届く（「紹介予約」ではないこと）
- [ ] メニュー ＞ **予約** に届いている。カードに「**REALPROOFからのご予約**」の1行
- [ ] 希望日時を選んで **この日時で確定する** → お客さん側に確定メールが届く
- [ ] 確定メールの件名が「**ご予約が確定しました**」（「ご紹介予約」ではないこと）
- [ ] 確定後、カードに**お客さんの名前・電話・メール**が出る

## D. 電話での確定（2分）

- [ ] 別の予約リクエストを作る（B をもう一度・**別のメールアドレス**で。同じアドレスは重複で弾かれる）
- [ ] 予約カードの「**お電話で決めた日時で確定する**」→ 日時を選ぶ → 警告が出る → OK
- [ ] 確定済みカードに「**お電話で確定した予約です**」が出る

## E. 受付を止める（1分）

- [ ] ホームのトグルを OFF → `/card/<ID>` から予約ボタンが消える
- [ ] メニュー ＞ 予約 の「紹介予約を受け付けています」トグルも同じ画面にある
- [ ] トグルを戻す

## F. 「自分のサイトで受け取る」（2分・外部URLを設定している場合）

- [ ] サービス設定 ＞ 予約の受け方 で「自分のサイトで受け取る」を選ぶ
- [ ] `/card/<ID>` の予約するが**自分のサイトへ飛ぶ**
- [ ] メニューの「このメニューで予約する」は**REALPROOFのまま**（仕様どおり）

## 見つかったら即報告してほしいもの（優先度順）

1. **予約が届かない / 通知が来ない** — 受け口の事故は最優先
2. 確定メールが届かない
3. 文言に「紹介」が残っている（直接予約なのに紹介予約と書いてある）
4. 見た目の崩れ

---

## 告知を送る前提

このチェックが通ってから `docs/announcements/2026-08-06-booking.md` の①②を配信する。

**理由**: 予約URLを設定していないプロは、本人が何もしなくても REALPROOF で予約を
受け取る状態になっている（§17-1の既定）。告知は「新機能のお知らせ」であると同時に
「**あなたのところに予約が届くかもしれないので通知先を確認してください**」という
安全のための連絡でもある。導線が壊れたまま告知すると、その両方が裏目に出る。
